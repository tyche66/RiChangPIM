# 07 实施路线图与验收标准

> 实施状态：本章是从当前验证级 AI 能力演进至目标架构的交付顺序。某阶段列出的能力只有通过该阶段退出条件后，才可标记为已实现或用于对外承诺。

## 1. 实施原则

- 先建立评测和安全基线，再扩大 UI 承诺；
- 先只读、后写入，先人审、后考虑自动化；
- 先统一 Gateway，再构建 Portal，避免前端绑定临时接口；
- 先完善真实产品数据，再评估推荐质量；
- 每阶段必须有可独立回滚的数据库迁移和功能开关；
- 不以 Sprint 日期代替退出标准。

## 2. 工作流

| 工作流 | 责任建议 |
| --- | --- |
| A 业务与数据 | 产品负责人 + 采购/销售代表 + 数据管理员 |
| B Gateway 与工具 | 后端负责人 |
| C 知识与 Worker | AI/后端工程师 |
| D Portal | 前端负责人 + 设计 |
| E 安全与评测 | 架构师 + 测试 + 安全负责人 |
| F 运维与成本 | 运维负责人 |

必须明确一名 AI 产品 Owner 和一名知识数据 Owner。没有数据责任人时，RAG 质量问题会长期被错误归因于模型。

## 3. Phase 0：基线与决策门

目标：在写核心功能前解决数据、权限、供应商和验收口径。

交付：

- 评审并冻结本架构规划；
- 为四类助手各选定业务负责人和 Top 场景；
- 整理首批不少于 200 条离线评测样本；
- 补齐试点产品可验证数据，不再用占位价展示；
- 确认主 Chat/Embedding 模型供应商、数据处理条款和预算；
- 轮换当前开发/演示环境使用过的模型凭据，并核验 Git 历史、日志和构建产物无泄露；
- 定义细粒度 AI 权限并完成角色映射方案；
- 形成 AI 威胁模型和数据分级清单；
- 建立现有 `/chat`、`/recommend`、RAG 的效果与延迟基线。

退出条件：

- 老板、产品、架构、安全和研发书面确认范围；
- 评测集覆盖权限、未知数据、拒答和攻击样本；
- 模型供应商可用但 Key 未进入代码和文档；
- 已完成既有模型凭据轮换，Secret scan 与 Git 历史核验无有效 Key；
- 试点数据足以验证至少销售选型与知识问答，不满足时先暂停功能开发。

## 4. Phase 1：统一只读智能层

目标：实现可信的统一查询，不执行任何业务写入。

交付：

- `POST /api/v1/knowledge/query` 与统一 SSE 协议；
- Policy、Planner、Tool Registry 基础框架；
- `product.search/get_many/compare`、`quality.summary/list_issues` 工具；
- 精确产品识别、产品知识卡片；
- 文档来源标准化和引用校验；
- `DigestConversationStore`；
- 细粒度 AI 权限迁移；
- Gateway 指标、trace、成本统计和功能开关；
- 现有管理前端可用一个内部调试页验证 API。

退出条件：

- 结构化事实准确率 100%；
- 产品实体精确识别率 ≥ 98%；
- 动态字段不从文档回答；
- 所有角色权限矩阵测试通过；
- 模型关闭时核心 PIM 全绿；
- 非流式与 SSE 契约测试通过。

## 5. Phase 2：知识生产化与 Portal MVP

目标：把说明书 RAG 从同步验证功能升级为可运营能力，并上线内部 Portal。

交付：

- `knowledge_document/chunk/index_job` 迁移；
- PostgreSQL Outbox + Redis Streams + Worker；
- PDF/DOCX/OCR 解析流水线与结构化切块；
- 精确 + 中文关键词 + pgvector + RRF；
- 来源页码、章节和打开原文；
- 索引任务后台、失败原因、重试和重建；
- 独立 `portal/`：首页、全屏流式对话、产品卡、比较表、来源抽屉；
- 移动端和可访问性；
- 反馈 API 与 UI。

退出条件：

- 说明书 Recall@10 ≥ 90%，引用准确率 ≥ 95%；
- 索引成功率 ≥ 99%，95% 普通资料 5 分钟内可检索；
- 删除/替换资料不会召回旧内容；
- Portal Desktop/Mobile E2E 全绿；
- 20 并发下不破坏核心 PIM 性能门禁；
- 10 万知识块容量报告完成。

## 6. Phase 3：销售与采购业务闭环

目标：让 AI 从只读查询进入受控业务协作。

交付：

- `pending_action` 模型与确认 API；
- 方案草稿篮、`proposal.create_draft/update_draft`；
- AI 方案说明生成版本、来源与确认人记录；
- `supplier.compare` 和采购辅助结果；
- 未知库存、待核价、草稿产品的 UI/答案规则；
- 分享创建仍由人工二次确认；
- 操作冲突、过期、幂等和撤销体验；
- 销售、采购用户试点与反馈闭环。

退出条件：

- 未经确认写入次数为 0；
- 幂等、重放、对象状态变化测试 100% 通过；
- 对外内容均能追踪生成模型、来源和确认人；
- 采购助手不对缺失的交期、质量或实时库存做推断；
- 业务代表对选定场景完成 UAT 签字。

## 7. Phase 4：优化与企业集成准备

目标：基于真实运营证据优化，而不是堆叠 Agent 功能。

候选交付：

- 基于评测收益引入 reranker；
- Query/Embedding 缓存；
- Embedding 双版本切换；
- 完整会话存储的隐私评审和可选实现；
- ERP/CRM/WMS Adapter 契约与字段时效模型；
- 文档级 ACL 和组织数据范围；
- 模型供应商影子评测和切换；
- 多模态图片/表格理解试验。

进入条件：前三阶段质量和运营指标稳定至少一个发布周期。任何候选能力必须有业务 KPI 和离线提升证据。

## 8. 数据库迁移策略

从当前 head `0012` 之后只新增迁移，不修改历史迁移：

1. 新增知识与任务表，不删除现有 `product_manual_chunk`；
2. 部署兼容读取；
3. 后台回填已有 Manual/Chunk；
4. 对比新旧检索结果；
5. Gateway 切读新表；
6. 保留至少一个稳定发布周期；
7. 再单独立项清理旧字段/表。

每次迁移必须验证：空 PG16 全链升级、现有数据升级、downgrade 策略（若不可逆需书面说明）、备份恢复、索引创建耗时和锁影响。

## 9. Feature Flags

建议：

```text
AI_PORTAL_ENABLED
KNOWLEDGE_GATEWAY_ENABLED
KNOWLEDGE_HYBRID_SEARCH_ENABLED
KNOWLEDGE_WORKER_ENABLED
AI_PENDING_ACTIONS_ENABLED
AI_PROCUREMENT_ENABLED
AI_FULL_CONVERSATION_STORE_ENABLED=false
AI_RERANKER_ENABLED=false
```

服务端是最终开关，前端开关只控制展示。关闭 AI 时返回明确 503/功能未启用，不伪装成功。

## 10. 测试矩阵

### 10.1 单元与契约

- Planner Schema、实体规则、工具参数；
- Policy 权限和字段过滤；
- RRF、去重、引用映射；
- 结构切块、表格、页码；
- SSE parser 和事件版本；
- 会话 Store 接口；
- 动作状态机、幂等和过期。

### 10.2 集成

- 真实 PG16 + pgvector；
- MinIO 附件解析；
- Redis Streams ack/pending/reclaim；
- 模型 Mock 的流式、超时、限流、坏 JSON；
- Worker 崩溃恢复和重复消费；
- 删除/替换/重建一致性。

### 10.3 安全

- 各角色、各工具、各字段笛卡尔权限测试；
- 水平越权 session/source/action；
- Prompt 注入和文档注入；
- 任意 SQL/URL/工具名；
- 敏感数据外发 Mock 断言；
- 日志、指标、审计无原文和密钥；
- 文件炸弹、错误 MIME、超大文档。

### 10.4 E2E

- 登录 Portal、流式问答、停止和重试；
- 产品搜索、比较、来源跳转；
- 待核价/库存未知显示；
- 数据质量查询；
- 采购权限差异；
- 加入方案草稿、确认、重复确认；
- AI/Redis/OCR/Worker 降级；
- Desktop 1280x800、Mobile 393x851。

## 11. AI 发布门禁

在现有 `RELEASE_GATE.md` 基础上新增硬门禁：

1. 固定离线评测集全量运行并生成版本化报告。
2. 结构化事实、动态字段通道、权限安全三项必须 100%。
3. 检索和引用达到 `06` 的最低标准。
4. 生产配置 Secret scan 无 AI Key、Prompt 原文和证书私钥。
5. 模型关闭、超时、限流、坏响应的降级测试全绿。
6. 10 万知识块容量和核心 PIM 干扰测试达标。
7. 新迁移通过空库、升级库和恢复演练。
8. Worker 队列、Dead jobs、索引新鲜度具备监控和告警。
9. 对外业务动作必须有人工确认 E2E。
10. 产品、架构、安全、测试和运维共同签字 GO。

## 12. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 当前产品数据不完整 | 推荐失真，业务不信任 | Phase 0 先治理数据；未知即未知 |
| 四类助手范围过大 | 首期失焦 | 统一底座，按阶段逐项开放，不并行造四套 Agent |
| 外部模型不稳定 | 超时、成本、不可用 | 超时/熔断/预算/降级，供应商可替换 |
| RAG 有召回无答案质量 | 错误引用和幻觉 | 评测集、混合检索、引用校验、拒答 |
| 权限只在 UI 控制 | 敏感泄露 | Policy + Tool + Query 三层服务端授权 |
| Worker 争抢 DB | 核心 PIM 变慢 | 独立连接池预算、低并发、优先级和压测 |
| 保存完整会话的需求提前出现 | 隐私设计被绕过 | 预埋 Store 接口，但功能 Flag 默认关闭 |
| 前后端临时接口固化 | 长期不一致 | Portal 只依赖统一 Gateway |

## 13. 立项后仍需老板确认

以下不阻塞本次架构规划，但阻塞对应实施阶段：

1. 主模型供应商、数据处理地域与月度预算上限。
2. `purchaser`、`viewer` 可用哪些助手及采购敏感字段的最终矩阵。
3. 首批试点部门、每类助手的业务验收人。
4. AI 生成方案说明是否需要额外免责声明模板。
5. 完整会话未来可能的保留期限，暂不启用。
6. 何时启动 ERP/CRM/WMS 集成需求调研。
