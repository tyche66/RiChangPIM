## 2. ERD 提案（全部新表；仅 2 处对既有表加可空列）

约定：均继承 CommonBase（id uuid、create_time/update_time、is_deleted/deleted_at）；下表省略公共列。软删除唯一约束一律用 partial unique（`WHERE is_deleted = false`），对齐 pending_action 的既有写法。

```text
User (现有)  ──1:N──  Customer.owner_sales_id
Customer 1──N Project 1──N ProjectMember N──1 User
Project  1──N ProjectAsset N──1 Attachment(现有, MinIO)
Customer/Project 1──N CustomerDialogue / Requirement / FollowUp
Proposal (现有) +project_id?/customer_id? 可空外键   Quotation 经 proposal 间接归集
ContentBatch 1──N ContentItem 1──N ContentPublication 1──N ContentMetricSnapshot
Reminder (独立) ── target_type/target_id 多态指向 content_item / follow_up / project
Notification (站内消息, assignee 收件箱)
```

### 2.9 新媒体四表
**content_batches**：title、customer_id?/project_id?/product_ids JSONB、topic text、platform varchar(32)（xhs/douyin/moments/seo/other）、requested_count int、status（pending/running/done/failed）、model_provider/model_name、created_by。

**reminders**：rule_code varchar(32)、target_type/target_id、assignee_id FK user.id、title、due_at timestamptz、status（pending|sent|done|snoozed|cancelled|overdue）、dedupe_key varchar(128) partial unique WHERE is_deleted=false、snoozed_until?、attempts int default 0、escalated bool default false。

**notifications**：user_id、title、body、kind（reminder|escalation|system）、read_at?。

## 3. 状态机

### 3.1 项目阶段（线性，允许回退但记录留痕）
`lead → measuring → design → quoted → producing → delivered → closed`，任意阶段可 → cancelled。阶段只有一级，无多级生命周期（对齐 HLD §七 修订）。

### 3.2 客户漏斗阶段（线性）
`lead → contacted → needs → quoted → won | lost`。won/lost 终态，lost 可 reopen 回 contacted。

### 3.3 内容条目状态
```
draft ─adopt→ adopted ─人工确认制成视频→ produced ─登记发布→ published ─录曝光→ tracking ─T+7已过→ closed
draft ─reject→ rejected（终态，可复制为新 draft）
published 后随时可补录快照；closed 后补录不改状态只加数据
```
迁移合法性在服务层校验，非法迁移返回 400（业务码）。

### 4.1 新增权限码（16 个，命名沿用 resource:action）


### 4.2 角色 × 权限
| 角色 | 新增权限 |
|---|---|
| admin | 全部（现有 `*` 直通，无需变更；admin 在 PermissionChecker 中直通） |
| sales | customer:view/edit、customer:export、project:view/edit/member、dashboard:view、跟进随 customer:edit、content:view、reminder:view/edit |
| designer（新） | project:view、project:edit、project:member（仅自己所在项目）、dashboard:view、reminder:view |
| operator（新） | content:view/generate/adopt/publish/metric/export、dashboard:view、reminder:view/edit、project:view（只读，用于内容关联）、customer:view（只读，脱敏） |
| purchaser / viewer | 不加（viewer 保持只读产品；如需看板后续再议） |

### 4.3 数据范围（行级）—— `apply_data_scope(query, user, model)`
叶子模块 `backend/app/core/data_scope.py`（只 import sqlalchemy 与模型，不依赖 app.main/database，满足 tests/unit 硬约定）：
- role_code = admin → 不加过滤（本期不设独立 manager 角色，用 admin 承担；若后续加 manager 只改此函数）。
- sales → Customer: `owner_sales_id == me`；Project: `customer.owner_sales_id == me OR exists(ProjectMember.project)`；子表按父 id 子查询过滤。
- designer → Project: `exists(ProjectMember where user_id==me)`；其下 asset/方案只读可见；Customer 仅经由被绑定项目反查（只读、脱敏）。
- operator → content 系全量；Project/Customer 只读全量（用于内容关联选择），不含 PII。
- 驾驶舱所有聚合必须过 apply_data_scope；sales 的聚合输出剔除成本/毛利类字段（本来不产出，另在序列化白名单再兜底一层）。

### 4.4 PII 规则
- 序列化层：无 `customer:pii` 时 phone/wechat/address 输出脱敏（`138****1234` / `w***` / 市一级）。
- 查看明文走独立端点 `GET /customers/{id}/pii`，挂 `customer:pii`，每次访问写 OperationLog（action=customer_pii_view, module=customers）。
- 导出走 `customer:export`，同样写日志；文件下载/预览沿用现有 token 机制。

## 6. 关键设计点

### 6.1 AI 边界（红线 4）
- 文案生成：AIServiceAdapter + 严格 JSON Schema（一次 N 条），产品参数/名称经 Business API（products 服务）回查后以 `verified_payload` 快照存储，AI 不得产出价格/规格/交期承诺；生成失败或校验不过 → 不写 content_items，batch 记 failed，不落任何 adopted 类状态。记录 model/time/generation_version。
- 需求提取：AI 结果只进 pending_action（payload），确认后才写 requirements(source=ai_extracted, confirmed=true)；取消/过期不污染业务表。
- AI_ADAPTER=none → 受控 503（沿用 factory/none.py 行为）；限流沿用 Redis 10/min（rate_limiter 挂 content.generate、requirements.extract）。

### 6.2 驾驶舱指标定义（Phase 3 先接客户/项目/销售/方案）
| 指标 | 数据源 | 可见角色 |
|---|---|---|
| 新增客户数（周/月趋势） | customers.create_time | 全角色（sales 仅本人范围） |
| 客户漏斗分布 | customers.stage | 同上 |
| 项目阶段分布 | projects.stage | 同上（designer 仅绑定项目） |
| 停滞项目（N 天无跟进，默认 7，可配） | projects ⨝ max(follow_ups.create_time) | 同上 |
| 逾期跟进数 | follow_ups.next_follow_at < now() 且未完成 | 同上 |
| 各销售跟进量排行 | follow_ups 按 follower 聚合 | admin 全量；sales 仅本人行 |
| 方案数/报价数/已确认报价额 | proposals/quotation（status=confirmed 的 total_amount） | admin 全量；sales 本人；designer/operator 不展示金额卡 |
| 我的待办 | reminders + follow_ups.next_follow_at | 各自本人 |
| 内容链路卡（Phase 4 前空态） | content_* | operator/admin |
- 价格类字段（已确认报价额）**不进 Redis 缓存**（强准确性红线）；其余聚合缓存 30–60s，key 含 user_id+role+范围哈希；Redis 异常降级直查。
- 无数据一律空状态/"待录入"，禁止占位假数据。

### 6.3 提醒规则（确定性规则决定"何时"，LLM 仅润色文案）
| 规则 | 触发 | dedupe_key | 完成条件 |
|---|---|---|---|
| R1 content_video_check | content_item → adopted | `content_video_check:{item_id}` | 标记 produced 或人工 done |
| R2 content_metric_{1,3,7} | publication 创建 | `content_metric:{pub_id}:T+n` | 录入任一快照 |
| R3 customer_follow_up | follow_up.next_follow_at | `follow_up:{followup_id}` | 新建跟进或 done/snooze |
| 升级 | pending 超期 24h | …:escalated | 通知 assignee 上级(admin)一次，escalated=true |
提醒文案 LLM 失败 → 模板文案降级。时间全部 UTC 存储、北京时间展示（前端复用 utils/beijingTime.ts）。

### 6.4 知识库隔离
requirements/customer_dialogues/pending_action payload 不写 doc_chunk、不进 Knowledge Gateway：新表无 KnowledgeSource 映射即默认隔离；在 knowledge 检索的 source allowlist（现为 product/manual/…）中确认不含 customer/project，Phase 2 加契约测试固化。
