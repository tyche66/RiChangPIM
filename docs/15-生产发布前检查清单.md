## 0. 先看结论

### 0.1 现在直接部署会发生什么（一句话）

如果按现有文档直接 `docker compose up -d --no-deps backend nginx`：

- 不会自动重建镜像，**很可能仍跑旧镜像，等于什么都没发**；必须先 `docker compose build`。
- 如果先 `build` 再 `up`，会从生产中点 `0024` 连续执行 `0025_crm_schema_compat` → `0026_catalog_attributes` → `0027_content_skills` → `0028_project_spaces` → `0029_project_remark` → `0030_content_dna_fields` 六个迁移（全部幂等），并自动写 4 个默认 Skill、属性词典种子和 RBAC 补齐（含 `content:manage`）；产品属性回填**不会**执行。
- 内容工坊/独立选题会**全部返回 503（50302）**，因为 `.env` 里没有 `CONTENT_AI_*`，且主 `AI_API_KEY` 不会自动复用。
- `portal/dist` 的 mtime（2026-10-22 17:18）早于 `portal/src/views/SharePage.vue`（2026-10-23 10:42）；虽然 dist 里已能看到部分新字段，但不能证明包含最后一次修改。按发布纪律必须重建 portal。
- 当前 `frontend/dist/index.html` 引用的是 `/assets/...`（根路径），不是 `/admin/assets/...`；**直接打 nginx 镜像会让后台白屏**，必须先跑 `build_frontends.sh`。
- 如果构建时没导出 `BUILD_ID` 等版本值，后台“版本”页会报前后端不一致。
- 如果迁移成功后想“秒回旧镜像”，**旧镜像会因为不认识 `0025`–`0030` 这些新 revision 而启动失败**；可靠回滚路径是恢复本次备份，不是降级。

### 0.2 发布硬阻断（GO/NO-GO）

在下列 4 项闭环前，**不建议进入生产窗口**：

1. **后端镜像会把 `backend/.env` 和 `backend/venv` 打进镜像**（`backend/Dockerfile` 的 `COPY . .` + `backend/` 下没有 `.dockerignore`）。必须先修构建上下文，并在构建后验证镜像内不存在 `/app/.env`。
2. **回滚假设不成立**：旧镜像不包含 `0025`–`0030` 迁移文件，迁移成功后无法直接回切；必须先核对旧镜像的 `alembic heads`，并接受“恢复备份”作为回滚路径。
3. **`CONTENT_AI_*` 未配置**：内容 AI 功能上线即 503。必须由用户提供 key/file，或明确接受该功能暂不可用。
4. **构建环境不完整**：当前 WSL 的 `$HOME/.nvm/versions/node/v24.18.0` 不存在，`scripts/build_frontends.sh` 无法按文档运行；`portal/dist` 旧于源码；`frontend/dist/index.html` 还是 `/assets/...` 根路径产物。必须先解决 Node 24 构建路径、重建两个前端，并验证 admin 是 `/admin/assets/...`。

### 0.3 仍需用户拍板

见第 8 节。最少需要确认：发布窗口、版本号、`CONTENT_AI_*`、`.dockerignore` 修复、Node 构建路径、nginx 超时、属性回填是否单独开窗。

## 2. 高风险点（按严重度）

### P0-1 后端镜像会把 `backend/.env` 和 `backend/venv` 打进镜像

**证据**：

- `backend/Dockerfile:28` 是 `COPY . .`。
- `backend/` 下存在 `.env`（4 KB）、`venv/`（333 MB）、`.venv/`、`回收站/`。
- 仓库只有**根目录** `.dockerignore`；`docker compose` 的 backend build context 是 `./backend`，Docker 只认 `backend/.dockerignore`，根目录那份不生效。`docker-compose.worker.yml` 也用同一 `./backend` 上下文，问题相同。

**影响**：

- 镜像内会包含 `DATABASE_URL`、`JWT_SECRET`、MinIO 账号口令等真实 secret；镜像一旦被导出/推送/共享即泄露。
- 镜像额外膨胀数百 MB，构建变慢。
- `backend/回收站` 等废弃文件也会进镜像。

**处置**：

- 发布前增加 `backend/.dockerignore`（至少排除 `.env`、`.env.*`、`venv`、`.venv`、`__pycache__`、`.pytest_cache`、`.ruff_cache`、`回收站`），或改用干净的构建上下文。
- 修好后首次构建建议 `docker compose build --no-cache backend`，避免旧层缓存；不要删除旧镜像（回滚要用）。
- 构建后必须验证：
  ```bash
  docker run --rm --entrypoint sh <backend-image> -c 'test ! -e /app/.env && test ! -e /app/venv && echo CLEAN || echo LEAK'
  ```
  输出必须是 `CLEAN`；`LEAK` 时禁止部署。
- 旧镜像可能也已经包含 `.env`；不要把任何 `richangpim*` 镜像推到公共 registry、导出给外部或写进发布包。

### P0-2 迁移成功后，旧镜像不一定能直接回切

**证据**：

- `0025_crm_schema_compat.py` 至 `0030_content_dna_fields.py` 是本次新增/重编号文件，旧镜像（生产 0024 链）的 `alembic/versions` 没有这六个 revision。
- `backend-entrypoint.sh:46` 每次启动都执行 `alembic upgrade head`。
- 如果 DB 已被升到 `0030`，旧镜像的 Alembic 会报 `Can't locate revision identified by '0030_content_dna_fields'`，容器直接退出。

**影响**：

- “保留旧镜像即可秒回滚”不成立；迁移成功后回切旧镜像可能让后端完全起不来。
- 此时只剩两条路：修前向（hotfix 新镜像）或恢复本次备份（会丢失备份后的写入）。

**处置**：

- 发布前在只读窗口核对旧镜像：
  ```bash
  docker run --rm --entrypoint sh <old-backend-image> -c 'cd /app && alembic heads'
  ```
  只有输出包含 `0030_content_dna_fields`，旧镜像才具备“迁移后回切”的最低条件；否则按“恢复备份”设计回滚。
- 本文不推荐、也不允许 `alembic downgrade`。

### P1-1 内容 AI 未配置，上线即 503

**证据**：

- `.env` 变量名清单中没有 `CONTENT_AI_*`（本次只列名，未读取值）。
- `docker-compose.yml` 将 `CONTENT_AI_API_KEY` 默认成空字符串。
- `backend/app/adapters/factory.py:112` 在无 key 时返回 `NoneAdapter`。
- `backend/app/api/v1/content.py:209` 和 `backend/app/api/v1/content_skills.py:467` 对 `NoneAdapter` 返回 `503 / 50302 / AI 能力中心未配置`。

**影响**：

- `POST /api/v1/content/batches`、`POST /api/v1/content/topics/runs` 不可用。
- 内容列表、Skill 管理、发布登记等非生成接口仍可用。
- `GET /api/v1/content/models` 仍返回模型清单（200），前端可能显示模型但生成失败。

**处置**：

- 用户提供 `CONTENT_AI_API_KEY` 或 `CONTENT_AI_API_KEY_FILE`；或明确接受该功能暂不可用并在发布说明中标注。
- 不要指望 `AI_API_KEY` 自动复用；内容域是独立配置。
- **不要把 key 只写进 `backend/.env`**：compose 会注入 `CONTENT_AI_API_KEY=${CONTENT_AI_API_KEY:-}`（即使为空也是“已设置的环境变量”），pydantic 的环境变量优先级高于 `.env`，会把 `backend/.env` 里的值覆盖成空。key 必须写在**根 `.env`**（compose 读取）或使用 `CONTENT_AI_API_KEY_FILE`。
- 设置 key 后需要重启 backend 才生效；重启会重置 admin 口令（见 P2-1）。

### P1-3 版本注入缺失会导致“前后端版本不一致”

**证据**：

- `.env` 当前 `APP_VERSION=1.9.4`、`BUILD_ID=dev-local`、`BUILD_TIME=unknown`、`GIT_COMMIT=unknown`。
- `docker-compose.yml` 同时把 `APP_VERSION/BUILD_ID/GIT_COMMIT/BUILD_TIME` 当 build args 和运行时 env，默认值就是 `dev/dev-local/unknown`。
- 后台“版本”页按 `build_id` 比对前后端。

**影响**：

- 如果构建/启动时没有 export `build_frontends.sh` 输出的那套值，后端会自报 `dev-local`，版本页显示不一致；发布追溯也失真。

**处置**：

- 构建前 export，且**同一条 shell 会话**里完成 `build` 和 `up`：
  ```bash
  export APP_VERSION=<build_frontends.sh 输出的 APP_VERSION>
  export BUILD_ID=<build_frontends.sh 输出的 BUILD_ID>
  export GIT_COMMIT=<build_frontends.sh 输出的 GIT_COMMIT>
  export BUILD_TIME=<build_frontends.sh 输出的 BUILD_TIME>
  export APP_ENV=production
  ```
- 发布后 `/api/v1/health` 的 `version` 必须是真版本号，不能是 `dev`。

### P1-4 nginx 默认 60s 读超时 vs 内容 AI 长调用

**证据**：

- `docker/nginx/conf.d/default.conf` 的 `location /api/` 没有设置 `proxy_read_timeout`，使用 nginx 默认 60s。
- `docker-compose.yml` 将 `CONTENT_AI_TIMEOUT` 默认成 60；`backend/app/core/config.py` 的默认值是 180。
- 内容生成/独立选题是一次同步上游调用，10 条选题可能明显超过 60s。

**影响**：

- nginx 可能先返回 504，而后端仍在生成并最终落库；用户重试会创建第二个批次。
- 恰好 60s 时是竞态：后端超时返回 422/503 与 nginx 504 可能同时发生。

**处置（二选一，需用户批准）**：

- 给 `/api/v1/content/` 增加专用 location：`proxy_read_timeout 300s; proxy_send_timeout 300s; proxy_buffering off;`；或
- 将 `CONTENT_AI_TIMEOUT` 降到 45s 左右，`CONTENT_AI_MAX_RETRIES=0`，接受更多超时失败。

### P1-5 每次启动都写 seed，且属性词典种子有长度/竞态风险

**证据**：

- `backend-entrypoint.sh:57` 每次启动执行 `seed_default_skills --apply`。
- `backend-entrypoint.sh:61` 每次启动执行 `seed_attribute_dictionary --apply`。
- `seed_attribute_dictionary.py:245` 用 `category.category_name` 同时做 `option.code` 和 `label`；`catalog_attribute_option.code` 是 `String(64)`，`category_name` 是 `String(128)`。
- `seed_default_skills.py` 没有 advisory lock；多副本同时启动可能撞 `uq_cs_code` 唯一索引。

**影响**：

- 任一种子抛异常都会因 `set -e` 让 backend 容器退出，生产 API 不可用；且此时迁移已提交，旧镜像无法直接回切（见 P0-2）。
- 类目名超过 64 字符会触发 `StringDataRightTruncation`，首次上线即失败。
- 每次重启都会新增“新类目”对应的 option，长期会累积；多副本首次启动有唯一键竞态。

**处置**：

- 发布前执行只读 SQL：
  ```sql
  SELECT count(*) FROM category WHERE char_length(category_name) > 64;
  ```
  结果必须为 0；否则先修数据或改种子逻辑，不得直接发布。
- 首次发布只启动 **1 个 backend 副本**，等 seed 完成后再考虑扩容。
- 接受“每次重启都会做幂等 seed 写入”的行为；不要把 backend 重启当成纯只读操作。

### P1-6 `scripts/release_gate.sh` 会用错误的 base 覆盖 admin 产物

**证据**：

- `scripts/release_gate.sh:52` 的“frontend production build”执行 `cd frontend && npm run build`，**没有** `VITE_BASE_PATH=/admin/`。
- `frontend/vite.config.ts` 的 base 是 `process.env.VITE_BASE_PATH || '/'`。

**影响**：

### 3.1 只执行 `docker compose up -d --no-deps backend nginx`

### 3.2 执行 `docker compose build backend nginx` 后再 `up`

1. `0025_crm_schema_compat`：幂等补建 CRM 明细表（`project_members` 等 7 张；生产若已由 create_all 建表则跳过）。
2. `0026_catalog_attributes`：`pg_trgm` + 4 张属性表 + `product.material_description` + 3 个 trgm 索引。

  1. 修前向，构建包含修复的新镜像；或
  2. 停 backend/worker，恢复本次备份到 0024，再启动旧镜像（会丢失备份后的写入）。
- **绝对不要** `alembic downgrade`、`UPDATE alembic_version`、删 volume。

### 5.10 命令顺序速查

> 详细说明见对应小节；这里只给顺序，避免漏步/错序。

| # | 命令/动作 | 写库 | 对应小节 |
| --- | --- | --- | --- |
| 1 | 第 4 节只读核对 + GO/NO-GO | 否 | 4.1–4.5 |

## 6. 幂等性与重复执行

| 命令/步骤 | 是否写库 | 可重复执行 | 备注 |
| --- | --- | --- | --- |
| `pg_dump` / `pg_restore -l` | 否（只读） | 是 | 备份验证 |
| `docker compose build` | 否 | 是 | 但每次构建都会把当前上下文打进镜像；先修 `.dockerignore` |
| `docker compose up -d --no-deps backend` | 是（迁移+seed） | 是，但有副作用 | 每次重启重置 admin 口令、补 seed |
| `alembic upgrade head`（entrypoint） | 是 | 是 | 0025–0030 有表/列/索引存在判断 |
| `init_admin` | 是 | 是 | **重置** admin 口令/角色/状态 |
| `seed_data` | 是 | 是 | 插入缺失角色/权限/映射；`create_all` 只建表 |
| `seed_default_skills --apply` | 是 | 是 | 按 code 跳过；无 advisory lock |
| `seed_attribute_dictionary --apply` | 是 | 是 | 按 code 跳过；每次补新类目；有 advisory lock |
| `backfill_product_attributes --check` | 否 | 是 | 默认只读 |
| `backfill_product_attributes --apply` | 是 | 是 | 按 (product, attribute, option) 跳过；需审批 |
| `fix_category_option_codes --check` | 否 | 是 | 只读 |
| `fix_category_option_codes --apply` | 是 | 是 | 合并/软删；需审批 |
| `docker compose up -d --no-deps nginx` | 否（DB） | 是 | 重新加载静态产物 |

**重复发布注意**：

- 第二次 `up backend` 会再次执行 `init_admin`，admin 密码回到 `.env` 值。
- 第二次 `seed_attribute_dictionary` 不会重复插入同 code，但会补新类目。
- 第二次 `up` 不会回滚迁移；Alembic 已到 head 时是 no-op。

## 7. 停止条件与回滚

### 7.1 立即停止（NO-GO/中止）

出现任一条，停止后续步骤，不要“再试一次”：

- 备份失败、`pg_restore -l` 失败、备份文件为 0 或 sha256 记录失败。
- 第 4 节发现 DB 版本不是 `0024_attachment_biz_domain_compat`。
- `0025`–`0030` 迁移日志出现错误，或 `alembic current` 不是 `0030`。
- 新镜像 `alembic heads` 不含 `0030`。
- 新镜像 `.env`/`venv` 检查为 `LEAK`。
- seed 抛异常、backend 容器退出。
- `/health/ready` 的 `components.db != ok`，或登录/产品列表/分享页 5xx。
- 磁盘空间低于阈值（`/health/ready` 的 `capacity_alert=true`）。
- 发布窗口超时且未完成回滚决策。

### 7.2 回滚路径（**禁止 downgrade**）

#### 场景 A：迁移失败，DB 仍 `0024`

1. 确认：
   ```bash
   docker exec richangpim-postgres-1 psql -U pim -d ai_pim -tAc "select version_num from alembic_version;"
   ```
2. 如果仍是 `0024_attachment_biz_domain_compat`：
   ```bash
   # 把旧镜像 tag 回 compose 使用的镜像名（通常是 richangpim-backend:latest；
   # 以 docker images 里旧镜像的 Repository:Tag 为准）
   docker tag <old-backend-image-id> richangpim-backend:latest
   docker compose up -d --no-deps backend
   ```
   旧镜像启动会再跑 `alembic upgrade head`（对其而言 head=0024，与库一致），是 no-op。
3. 启动旧 nginx（如果已切换）：
   ```bash
   docker tag <old-nginx-image-id> richangpim-nginx:latest
   docker compose up -d --no-deps nginx
   ```
4. 记录失败日志，修前向后重新走发布流程。

#### 场景 B：迁移成功（DB 已 `0030`），seed/应用失败

旧镜像如果不含 `0025`–`0030`（生产镜像必不含），**不能**直接 `up`。两条路：

**B1. 修前向（优先）**

- 在代码/配置中修复失败原因，重新 `build backend`，再 `up -d --no-deps backend`。
- 适用于：seed 数据问题（如类目名 >64）、内容配置问题、应用 bug。
- 注意：每次 `up` 会重跑 `init_admin`/seed；修复后应一次成功。

**B2. 恢复备份（需单独批准，破坏性）**

1. 停止写入：
   ```bash
   docker compose stop backend
   docker compose -f docker-compose.worker.yml stop worker 2>/dev/null || true
   ```
2. 确认备份文件与 sha256 匹配：
   ```bash
   sha256sum -c backups/pre_upgrade_<TS>.sqlc.sha256
   ```
3. 恢复：
   ```bash
   docker exec -i richangpim-postgres-1 pg_restore -U pim -d ai_pim \
     --clean --if-exists --no-owner < backups/pre_upgrade_<TS>.sqlc
   ```
4. 确认 `alembic_version` 回到 `0024_attachment_biz_domain_compat`。
5. 启动旧镜像（先 tag 回旧镜像 ID）：
   ```bash
   docker tag <old-backend-image-id> richangpim-backend:latest
   docker tag <old-nginx-image-id> richangpim-nginx:latest
   docker compose up -d --no-deps backend
   docker compose up -d --no-deps nginx
   ```
6. 记录：备份后的写入会丢失；需业务确认。

> 恢复脚本 `scripts/db_restore.sh` 默认连 `localhost:5432/ai_pim`，在本机是错的；不要用它。必须用上面的 `docker exec` 显式路径。

### 7.3 失败阶段与处置对照

| 失败阶段 | DB 版本 | 旧镜像能否直接启动 | 首选处置 |
| --- | --- | --- | --- |
| 备份前 | 0024 | 能 | 修复后重来 |
| 迁移中（0025–0030 任一失败回滚） | 0024 或中间 revision | 不能（未知 revision） | 前向修复；或恢复备份到 0024 |
| 迁移成功、seed 失败 | 0030 | 不能（旧镜像无 0025–0030） | 前向修复；否则恢复备份 |
| backend 启动后健康失败 | 0030 | 同上 | 查 `/health/ready`、日志；前向修复 |
| nginx 切换后前端白屏 | 0030 | 旧 nginx 镜像可回切（静态） | 回切旧 nginx；backend 不动 |
| 内容生成 503 | 0030 | 不适用 | 配置 `CONTENT_AI_*`；不是回滚理由 |

### 7.4 禁止动作

- `alembic downgrade`（任何 revision）。
- `UPDATE alembic_version SET version_num=...`。
- `docker volume rm` / `docker compose down -v`。
- 删除 `backups/`、旧镜像、旧 dist。
- 在未备份时启动新 backend。
- 把 `.env`、token、密钥值贴进聊天/日志/文档。
- 默认执行 `backfill_product_attributes --apply`。
- 用 `scripts/db_restore.sh` 默认参数恢复生产。
