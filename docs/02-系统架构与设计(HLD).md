## 一、系统架构总览

AI-PIM 采用标准的**互联网企业级四层软件架构**，核心原则是：**业务逻辑由数据库与 Business API 维护，AI 只负责理解、生成与推荐，所有业务统一走 Business API。**

### 1.1 四层架构职责划分

| 架构分层 | 核心技术选型 | 职责说明 |
| --- | --- | --- |
| **表现层 Presentation** | Vue3, Vite, Element Plus, Pinia | 用户交互。区分企业内部 PC 端管理后台与外部客户 H5 分享页面。 |
| **业务层 Business** | FastAPI (Python) | 系统核心枢纽（Business API）。处理企业级业务逻辑、数据校验、权限控权，提供标准 RESTful API。 |
| **服务层 Service** | MinerU, Gotenberg, AI Service Adapter | 提供公共原子服务。通过 AI Service Adapter 抽象统一 AI 接口，实现下游 AI 引擎可插拔。 |
| **基础设施层 Infrastructure** | PostgreSQL, Redis, MinIO, Docker/Nginx | 底层数据存储、缓存、全文检索（pgvector 向量扩展，维度随 Embedding 模型配置）及容器化运行环境。 |

### 1.2 架构关键设计决策

1. **Business API 为核心枢纽**：所有业务操作（CRUD、权限校验、数据确认）统一走 Business API，表现层不直接访问数据库，服务层不越权处理业务逻辑。
2. **AI 能力可插拔**：通过 `AIServiceAdapter` 抽象基类定义统一接口契约，下游引擎（FastGPT / Dify / RagFlow）可热切换，业务层零改造。
3. **数据解耦红线**：AI 能力中心**永远不负责**价格、库存、供应商、客户隐私等强准确性数据的维护。大模型只负责"理解与生成"，真实数据必须由 Business API 从关系型数据库实时调取。
4. **向量检索与业务数据回查分层**：向量召回只提供"候选集"，强准确性字段必须由 Business API 二次查询数据库确认，形成 `AI能力中心 → Business API → 关系型数据库` 的闭环回查路径。

## 二、核心模块说明

业务层共包含 **12 个核心业务中心**，按职责域划分为五大类。

### 2.1 基座域：用户中心 / 权限中心

| 模块 | 职责 | 功能范围 | 交互方式 |
| --- | --- | --- | --- |
| **用户中心** | 用户账号生命周期管理 | 用户注册、登录、信息维护、角色分配 | 被**所有业务模块**依赖，提供身份上下文 |
| **权限中心** | RBAC 多级权限控制 | 菜单权限、按钮权限、接口权限、**字段级权限** | 被所有模块依赖；在 FastAPI 响应序列化层做统一字段过滤（如 `cost_price`、`supplier_id`），形成"查询层 + 响应层"双重防线 |

**字段级权限隔离示例：**
- 销售角色：可查看产品参数、AI 推荐、方案生成，**严禁查看成本价**
- 采购/产品经理：可配置产品参数、维护成本价与供应商链条
- 外部客户：无需登录，仅拥有被分享 H5 页面的**只读权限**

### 2.2 基础数据域：分类 / 品牌 / 标签 / 供应商 / 文件中心

| 模块 | 职责 | 功能范围 | 交互方式 |
| --- | --- | --- | --- |
| **分类中心** | 三级分类树管理 | 分类 CRUD、树形层级维护 | 被产品中心强依赖，提供 `category_id` 索引维度 |
| **品牌中心** | 品牌主数据管理 | 品牌 CRUD、品牌关联 | 被产品中心依赖 |
| **标签中心** | 标签体系管理 | 标签 CRUD、产品标签多对多关联（`ProductTag` 中间表） | 被产品中心依赖，支撑 AI 推荐的标签匹配 |
| **供应商中心** | 供应商主数据与供货链 | 供应商基础信息、合作状态、一对多供货追溯 | 被产品中心依赖；采购角色可见，销售角色字段级屏蔽 |
| **文件中心** | 多媒体文件统一管理 | 图片/视频/说明书 PDF 上传、存储、引用 | 被产品中心（附件）、方案中心（物料）、分享中心（PDF 导出）依赖；对接 MinIO 对象存储与 MinerU OCR |

### 2.3 核心实体域：产品中心

| 模块 | 职责 | 功能范围 | 交互方式 |
| --- | --- | --- | --- |
| **产品中心** | 产品主数据管理 | 产品编号、品牌、供应商、三级分类、标签、面价、成本价、材质、库存状态、多媒体文件；Excel 批量导入导出、一键克隆、上下架归档 | **系统核心枢纽**。向上依赖分类/品牌/标签/供应商/文件 5 个基础数据模块；向下被方案中心、报价中心、分享中心、数据统计中心依赖；通过 AI Service Adapter 调用 AI 能力（智能推荐场景） |

### 2.4 销售交易域：方案 / 报价 / 分享中心

| 模块 | 职责 | 功能范围 | 交互方式 |
| --- | --- | --- | --- |
| **方案中心** | 销售方案生成与管理 | 勾选产品自动拉取多媒体物料、AI 润色、推荐理由生成、方案明细（`Proposal` + `ProposalItem`） | 依赖产品中心（强）、文件中心（物料）；调用 AI 能力中心（润色/生成）；被报价中心、分享中心依赖 |
| **报价中心** | 动态报价单管理 | 产品数量、税率、特定折扣动态调价、HTML 模板渲染、高保真 PDF 导出（Gotenberg） | 依赖产品中心（面价/成本价）、方案中心（方案明细）；被分享中心依赖 |
| **分享中心** | 对外分享与安全风控 | 生成唯一安全 URL 与二维码、PDF/H5 导出、访问控制（公开/密码保护/到期失效/限制次数） | 依赖方案中心、报价中心、文件中心；通过 `ShareToken` 表统一管理 token、密码、过期时间、访问次数、审计记录 |

### 2.5 分析域：数据统计中心

| 模块 | 职责 | 功能范围 | 交互方式 |
| --- | --- | --- | --- |
| **数据统计中心** | 业务数据分析看板 | 产品统计、方案/报价汇总、分享访问审计（`ShareLog`）、操作日志（`OperationLog`） | **只读依赖**产品中心、方案中心、报价中心；不产生写操作，耦合度低 |

### 2.6 AI 能力中心（服务层）

AI 能力中心位于服务层，通过 `AIServiceAdapter` 抽象基类定义统一接口契约，解耦业务系统与下游 AI 引擎。

**接口契约（4 个核心方法）：**

| 方法 | 说明 |
| --- | --- |
| `chat()` | 统一对话接口（非流式），返回包含 `answer`、`sources`、`tool_calls` 的标准化 Dict |
| `chat_stream()` | 统一流式对话接口，异步生成器输出 SSE 数据帧 |
| `parse_tool_calls()` | 统一解析下游平台 Tool Call / Function Call 格式，抹平差异 |
| `manage_session()` | 统一会话生命周期管理（创建、拉取、删除历史） |

**六大核心应用场景：**

1. **文档知识检索（RAG）**：解析产品说明书/技术参数表，回答技术硬指标问题
2. **产品智能推荐**：理解用户模糊意图 → 转标准化筛选条件 → 调用 Business API 精准匹配
3. **AI 方案生成与润色**：对销售勾选的产品组合进行亮点提炼、行业话术修饰
4. **AI 营销文案生成**：根据产品参数生成多渠道文案（小红书/朋友圈/SEO/短视频脚本）
5. **AI 销售与培训助手**：赋能内部员工，解答产品竞争优势与区别

**可插拔下游引擎：** FastGPT / Dify / RagFlow → 统一对接 DeepSeek / Qwen / OpenAI 等 LLM API。

## 三、数据流说明

系统存在三条核心业务数据流，覆盖产品资产沉淀、AI 智能推荐、方案生成分享全链路。

### 3.1 数据流一：产品上传与知识归档

**输入来源：** 管理员上传产品结构化数据（Excel/表单）+ 附件（PDF 说明书）

**数据传递路径与变换过程：**

```
[管理员] 上传结构化数据 + PDF
    │
    ▼
[MinerU 服务] OCR 自动化解析 PDF
    │
    ├──→ [PostgreSQL] 写入业务数据库（结构化参数：型号、规格、价格等）
    │
    └──→ [AI 能力中心] 提取标签与向量化入库（知识库 / pgvector）
    │
    ▼
[管理员] 人工最终校验 → 一键上架发布
```

**数据变换说明：**
- PDF 附件经 MinerU OCR 解析为结构化文本
- 结构化文本分为两路：一路写入 PostgreSQL 业务表（`Product` / `Attachment` / `ProductManual`），一路经 AI 能力中心提取标签并向量化存入 pgvector
- 双写完成后进入人工校验环节，管理员确认数据准确性后执行上架（`status` → `active`）

**最终输出：** 产品上架生效，可被检索、推荐、方案引用

### 3.1.1 事务边界与失败处理

产品入库为"双写"操作（PostgreSQL 业务数据 + pgvector 向量数据），事务边界定义如下：

**MVP 阶段（同步双写，强一致）**：
- 业务数据与向量化在同一数据库事务中
- 向量化失败则整体回滚，确保业务数据与向量数据严格一致
- 适用场景：数据量小，写入频次低，一致性优先

**V1+ 阶段（异步补偿，最终一致）**：
- 业务数据先入库提交，向量化走消息队列异步处理
- 向量化失败自动重试3次，仍失败则标记 product.vector_status='pending'
- 后台任务定期扫描 pending 记录补偿
- 适用场景：数据量大，写入频次高，吞吐优先

> MVP 选择同步双写的理由：实现简单，数据一致性有保障，且 MVP 数据量小不会成为瓶颈。

### 3.2 数据流二：AI 智能产品推荐（含回查闭环）

**输入来源：** 客户/销售输入模糊需求（自然语言，如"预算5万、现代风、会议室投影设备"）

**数据传递路径与变换过程：**

```
[客户/销售] 模糊需求（自然语言）
    │
    ▼
[AI 能力中心] 语义理解与意图拆解
    │  转换为标准结构化检索参数（JSON）
    │  例：{ style: "modern", scene: "meeting_room", max_price: 30000 }
    ▼
[Business API] 执行多维度条件组合查询（SQL）
    │
    ├── 向量召回：提供候选集（pgvector 混合检索）
    │
    └── 关系型回查：价格/库存/供应商等强准确性字段二次确认  ← 闭环回查
    │
    ▼
[AI 能力中心] 组织润色话术并结构化呈现
    │
    ▼
[客户/销售] 获取推荐结果（含 answer + sources + tool_calls）
```

**关键数据边界（红线）：**
- 向量召回**只负责**提供"候选集"，不能直接作为最终事实数据输出
- 价格、库存、供应商、客户隐私等强准确性字段，**必须**由 Business API 再次查询数据库二次确认
- "向量召回结果 + 业务字段回查"作为一个统一执行链路，确保最终输出始终基于可信数据

**最终输出：** 结构化推荐结果，包含自然语言回答 + 引用来源 + 标准化检索参数

### 3.3 数据流三：销售方案生成与对外分享

**输入来源：** 销售在管理后台勾选产品组合（A / B / C）

**数据传递路径与变换过程：**

```
[销售] 勾选产品 A, B, C
    │
    ▼
[方案中心] 一键生成基础方案（自动拉取多媒体物料）
    │
    ▼
[AI 能力中心] 执行商务语境润色 + 推荐理由生成
    │
    ▼
[分享中心] 一键导出 PDF / 生成 H5
    │  生成唯一安全 URL + 二维码
    │  配置访问控制（密码/到期/次数限制）→ 写入 ShareToken 表
    ▼
[客户] 手机端扫码查阅（带权限校验）
```

**数据变换说明：**
- 方案中心将勾选产品组装为 `Proposal` + `ProposalItem` 明细，拉取关联多媒体物料
- AI 能力中心对方案进行亮点提炼、行业话术修饰、推荐理由生成
- 分享中心将方案渲染为 HTML 模板，经 Gotenberg 转为 PDF，或生成 H5 页面
- 分享凭证（token、密码、过期时间、访问次数）统一收敛到 `ShareToken` 表
- 客户扫码访问时，分享中心校验 `ShareToken` 状态与权限，记录访问审计到 `ShareLog`

**最终输出：** 客户通过 H5/PDF 查阅方案，访问行为被审计记录

## 四、模块间依赖关系

### 4.1 依赖关系总览

模块间依赖分为两类：**直接依赖**（数据/逻辑耦合，实线）与 **AI 能力调用**（松耦合，虚线）。

| 依赖方 | 被依赖方 | 依赖类型 | 耦合程度 | 说明 |
| --- | --- | --- | --- | --- |
| 产品中心 | 分类/品牌/标签/供应商/文件中心 | 直接 | **强** | 产品多维属性强引用基础数据 |
| 方案中心 | 产品中心 | 直接 | **强** | 方案明细依赖产品实体 |
| 方案中心 | 文件中心 | 直接 | 中 | 拉取多媒体物料 |
| 报价中心 | 产品中心 | 直接 | **强** | 面价/成本价计算 |
| 报价中心 | 方案中心 | 直接 | 中 | 基于方案明细生成报价 |
| 分享中心 | 方案中心 | 直接 | **强** | 分享对象主体 |
| 分享中心 | 报价中心 | 直接 | 中 | 报价单 PDF 导出 |
| 分享中心 | 文件中心 | 直接 | 中 | 文件存储与引用 |
| 数据统计中心 | 产品/方案/报价中心 | 直接（只读） | **低** | 只读分析，无写操作 |
| 全部业务模块 | 用户中心 / 权限中心 | 直接 | **强（横切）** | 身份鉴权与权限控权，横切所有模块 |
| 方案中心 | AI 能力中心 | AI 调用 | **松（适配器）** | 经 AIServiceAdapter 调用，可插拔 |
| 产品中心 | AI 能力中心 | AI 调用 | **松（适配器）** | 智能推荐场景调用，可插拔 |

### 4.2 依赖层次结构（自上而下）

```
输出层    │ 分享中心        数据统计中心（只读）
            │      ↓                ↓
销售域     │ 方案中心  ←──  报价中心
            │      ↓                ↓
核心域     │      产品中心
            │        ↓
基础数据   │ 分类 · 品牌 · 标签 · 供应商 · 文件
            │        ↓
基座       │ 用户与权限中心（RBAC · 字段级权限）

横切服务   │ AI 能力中心（Service Adapter）  ← 方案中心 / 产品中心 调用（松耦合）
```

### 4.3 耦合程度分级说明

| 耦合级别 | 定义 | 典型场景 | 改造影响 |
| --- | --- | --- | --- |
| **强耦合** | 模块间存在外键级数据引用，一方变更直接影响另一方 | 产品↔分类/品牌/标签；方案↔产品；分享↔方案 | 需同步改造，影响范围大 |
| **中耦合** | 模块间存在数据读取或流程依赖，但无强外键约束 | 报价↔方案（基于明细生成）；分享↔报价（PDF 导出） | 可独立演进，需接口兼容 |
| **低耦合** | 只读依赖，无写操作 | 数据统计↔产品/方案/报价 | 可独立扩展，几乎无影响 |
| **松耦合（适配器）** | 经抽象接口调用，下游可热切换 | 业务模块→AI 能力中心（经 AIServiceAdapter） | 下游引擎切换零改造业务层 |
| **横切耦合** | 全局性基础设施依赖 | 全部模块→用户/权限中心 | 需全局统一，不可绕过 |

### 4.4 关键解耦设计

1. **AI 适配器解耦**：业务层仅依赖 `AIServiceAdapter` 接口契约，不直接依赖 FastGPT/Dify/RagFlow 任何具体实现。切换 AI 引擎只需新增适配器实现类，业务层零改造。
2. **分享凭证独立收敛**：分享链接的 token、密码、过期时间、访问次数、状态独立收敛到 `ShareToken` 表，避免散落在 `Share` 表中，降低分享配置与分享主体的耦合。
3. **向量检索与业务查询分层**：向量召回（pgvector）与关系型数据查询（PostgreSQL 业务表）严格分层，AI 不直接输出强准确性数据，通过 Business API 回查闭环确保数据可信。

## 五、数据库设计概要（关联说明）

系统底座由 **23 张核心表**构成，核心实体关系与模块对应如下：

| 数据域 | 核心表 | 对应模块 |
| --- | --- | --- |
| 用户与权限 | `User`、`Role`、`Permission`、`RolePermission` | 用户中心 / 权限中心 |
| 产品核心 | `Product`、`Category`、`Tag`、`ProductTag`、`Brand`、`Supplier` | 产品中心 + 基础数据域 |
| 资产存储 | `Attachment`、`ProductImage`、`ProductManual` | 文件中心 |
| 销售交易 | `Proposal`、`ProposalItem`、`Quotation`、`QuotationItem` | 方案中心 / 报价中心 |
| 流转审计 | `Share`、`ShareToken`、`ShareLog`、`OperationLog`、`AIConversation` | 分享中心 / 数据统计中心 / AI 能力中心 |

**统一设计规约：**
- 主键：`id (UUID v7)`
- 时间戳：所有表必须包含 `create_time` 和 `update_time`
- 软删除：统一增加 `deleted_at`（时间戳）+ `is_deleted`（布尔），业务层禁止物理删除
- 向量字段：`Product` 表预留 `vector` 字段（pgvector），支撑混合检索
- 多租户预留：后续版本在主键外增加 `tenant_id` 作为统一分区维度

## 六、接口设计规范（关联说明）

所有接口遵循标准 RESTful 规范，统一采用 JWT 身份鉴权。

**核心接口示例：**

| 接口 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |

## 七、系统边界（不做什么）

本系统**不属于** ERP、MES、CRM 或财务软件。系统通过标准 REST API 与企业现有的钉钉、企业微信、外部 CRM 等系统进行解耦式集成，**坚决不越界处理**复杂的财务对账、生产制造工序或多级客户生命周期管理。

**安全防护体系：**
- 网络与传输：全站 HTTPS，关键接口 Redis 令牌桶限流
- 数据防注入：ORM 框架层严格参数化查询，杜绝 SQL 注入与 XSS
- 内容安全：文件上传预留流式病毒检测与扩展名强白名单校验

## 八、缓存策略（Redis）

### 8.1 缓存场景

| 场景 | Key 格式 | TTL | 失效策略 |
| --- | --- | --- | --- |
| 用户会话 | session:{user_id} | 2h（同JWT） | 登出时删除 |
| 用户权限码 | perms:{user_id} | 1h | 角色权限变更时删除 |
| 产品详情 | product:{id} | 30min | 产品更新/删除时删除 |
| 分类树 | category:tree | 1h | 分类变更时删除 |
| ShareToken 校验 | share_token:{token} | 5min | 撤销分享时删除 |
| 限流计数 | rate:{user_id}:{api} | 1min | 自然过期 |

### 8.2 缓存原则

- 只缓存读多写少且一致性要求不极高的数据
- 价格/库存等强准确性字段不缓存（直接查库）
- 缓存失败不阻断业务（降级直查数据库）
- 写操作采用 Cache-Aside 模式：先更新DB，再删除缓存
