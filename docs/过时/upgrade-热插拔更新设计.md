# RiChangPIM 热插拔更新设计

## 1. 文档定位

本文档定义 RiChangPIM 本地构建版和云端公测版的更新、回滚、数据保护和验收方案。

本文档解决四个问题：

- 更新时尽量不影响正在访问的用户；
- 更新不删除 PostgreSQL、MinIO、Redis 中的业务数据；
- 新版本启动失败或验收失败时，可以快速切回旧版本；
- 公测期间允许较大改动，但不把不可逆数据库迁移伪装成“零风险热更新”。

本文档是设计和操作约束，不代表所有步骤已经由现有脚本自动实现。当前仓库已有备份、恢复、健康检查和自动迁移能力，蓝绿服务编排、流量切换和发布状态机需要按本文档补齐后才可称为完整热插拔发布。

## 2. 目标与非目标

### 2.1 目标

| 目标 | 要求 |
| --- | --- |
| 应用更新 | 新版本先启动、预热、检查，通过后再切流量 |
| 用户可用性 | 正常代码更新不主动中断已有请求；短连接请求切换期间继续完成 |
| 数据安全 | 更新和回滚不得删除 Docker 命名卷；更新前必须有可验证的数据库和文件备份 |
| 回滚 | 支持代码快速回滚；支持按备份批次恢复数据库和 MinIO |
| 版本可追踪 | 记录版本号、构建 ID、Git commit、数据库迁移 head、备份批次 ID |
| 公测适应性 | 支持高频前端更新，也支持后端和数据库的分阶段发布 |

### 2.2 非目标

- 不承诺对任意破坏性数据库迁移提供真正零停机回滚；
- 不通过删除并重建 Docker volume 来“解决”升级问题；
- 不把 Redis 缓存当作唯一数据源；
- 不在生产环境直接使用 `git pull` 后覆盖正在运行的静态目录；
- 不允许旧版本和新版本长期共享互不兼容的数据库结构。

## 3. 当前系统基线

### 3.1 部署模式

当前项目有两条运行链路：

1. **本地构建版**：`docker-compose.yml` 启动 nginx、backend、PostgreSQL、Redis、MinIO、OCR 等服务。nginx 镜像在构建时复制 `frontend/dist` 和 `portal/dist`。
2. **云端公测版**：`scripts/start_demo.sh` 启动 `scripts/pim-demo-server.mjs`，直接提供宿主机上的 `frontend/dist`、`portal/dist`，并将 `/api`、`/health`、`/docs` 等请求代理到后端。

两种模式通常共用同一个后端数据栈，但必须确认实际环境中的 Compose project name、volume 名称和后端地址，不能仅凭目录名判断。

### 3.2 持久化数据

生产 Compose 当前使用固定命名卷：

| 数据 | 当前卷/位置 | 更新规则 |
| --- | --- | --- |
| PostgreSQL | `richangpim_go_postgres_pg16_data_20260716` | 只允许数据库容器复用；禁止随发布删除 |
| Redis | `richangpim_go_redis_data_20260716` | 主要用于缓存/队列；更新前后保持卷不变 |
| MinIO | `richangpim_go_minio_data_20260716` | 产品文件、图片等对象数据；禁止随发布删除 |
| 备份 | 宿主机 `./backups` | PostgreSQL 和 MinIO 必须同一批次备份 |

`docker compose up -d --force-recreate` 只重建容器本身时，命名卷不会被删除。但以下命令或操作具有数据破坏风险：

```bash
docker compose down -v
docker volume rm <volume>
rm -rf <数据库数据目录>
```

发布脚本必须拒绝执行上述操作。

### 3.3 当前启动行为

backend 容器启动时执行：

1. 等待 PostgreSQL 可连接；
2. `alembic upgrade head`；
3. 幂等初始化管理员；
4. 幂等写入 RBAC 种子数据；
5. 启动 uvicorn。

这保证了新容器可以自动补齐迁移，但不等于迁移本身可回滚。特别是删除列、删除表、修改数据语义等操作，执行成功后旧版本可能立即无法运行。

### 3.4 当前备份能力

`scripts/backup.sh` 已经具备以下能力：

- PostgreSQL 和 MinIO 使用同一 `BATCH_ID`；
- 每个组件写入 manifest 和 SHA-256；
- 临时文件成功后再原子改名；
- 任一组件失败时整体标记为 `incomplete` 或 `failed`；
- `scripts/db_restore.sh` 支持 PostgreSQL 恢复；
- `scripts/minio_restore.sh` 支持恢复到明确指定的 MinIO 目标。

因此，发布系统应复用这些脚本，不应另写一套没有校验的临时备份逻辑。

## 4. 总体架构

热插拔发布采用四层隔离：

```text
                    用户
                      |
              nginx / demo server
                      |
          +-----------+-----------+
          |                       |
   active backend           standby backend
       blue                    green
          |                       |
          +-----------+-----------+
                      |
       PostgreSQL / MinIO / Redis
       固定持久卷，不随发布删除
```

### 4.1 后端：蓝绿切换

- 同时保留 `blue` 和 `green` 两个应用槽位；
- 当前槽位继续接收流量；
- 新版本部署到非当前槽位；
- 新槽位完成启动、迁移、健康检查和冒烟测试后，才切换代理；
- 切换通过后保留旧槽位一段观察时间，不立即销毁；
- 观察期内发生故障，优先把流量切回旧槽位。

蓝绿切换只隔离应用进程，不隔离共享数据库。因此数据库迁移仍必须遵守兼容性规则，不能把“有两个 backend 容器”误认为“有两个数据库版本”。

### 4.2 前端：版本目录原子切换

前端发布不能直接在正在被 nginx 或 Node 读取的目录上逐文件覆盖，否则可能出现新 `index.html` 引用旧资源、或旧 `index.html` 引用已经被覆盖的资源。

推荐保留版本目录：

```text
/srv/richangpim/releases/
  20260803T120000Z-v1.10.0-abc1234/
    frontend/dist/
    portal/dist/
    release.json
  20260803T130000Z-v1.10.1-def5678/
    frontend/dist/
    portal/dist/
    release.json
/srv/richangpim/current -> releases/20260803T120000Z-v1.10.1-def5678
```

构建完成且校验通过后，先写入新目录，再以同一文件系统上的原子 `rename` 或符号链接替换更新 `current`。旧目录在观察期内保留，回滚只需要将 `current` 指回旧版本。

对于当前公测 Node 静态服务器，服务进程需要从稳定的 `current` 路径解析每个请求，或在发布时启动第二个静态服务器并切换入口。不能在进程启动时只读取一次带版本号的绝对路径，否则切换符号链接不会生效。

对于当前 nginx Docker 镜像，推荐使用两个 nginx 静态槽位或把发布目录作为只读 bind mount；不推荐用 `docker cp` 对正在服务的目录逐文件覆盖。若继续使用镜像内静态文件，则必须构建新 nginx 容器、健康检查通过后切换 nginx 入口。

## 5. 发布对象与版本记录

每一次发布必须生成一个不可变的 `release.json`，至少包含：

```json
{
  "release_id": "20260803T120000Z-v1.10.0-abc1234",
  "app_version": "1.10.0",
  "build_id": "cloud-20260803T120000Z",
  "git_commit": "abc1234",
  "build_time": "2026-08-03T12:00:00Z",
  "backend_image": "sha256:...",
  "frontend_sha256": "...",
  "portal_sha256": "...",
  "migration_head": "0018_example",
  "backup_batch_id": "20260803T115500Z-host-123",
  "previous_release_id": "20260802T100000Z-v1.9.0-def5678"
}
```

`release_id`、镜像 digest、构建产物摘要和数据库迁移 head 必须进入发布日志。不能只记录 Git 分支名，因为分支会继续变化。

现有版本元数据注入入口是 `scripts/build_frontends.sh`，后端版本由 `APP_VERSION`、`BUILD_ID`、`GIT_COMMIT`、`BUILD_TIME` 等环境变量注入。发布系统必须确保前后端使用同一组版本值，避免版本页出现前后端不一致。

## 6. 标准发布流程

### 6.1 发布前门禁

发布前必须满足：

1. 工作区和目标 commit 已确认，发布产物可重建；
2. `RELEASE_GATE.md` 中的测试、迁移、Compose 校验和依赖审计通过；
3. 当前服务健康，当前活跃槽位和 release ID 已记录；
4. 备份目录有足够空间；
5. 备份策略正常，最近一次完整备份状态为 `ok`；
6. 本次迁移已标记为 expand/contract，或明确批准维护窗口；
7. 新版本和旧版本的 API、数据库兼容性已检查；
8. 发布人已确定回滚目标 release ID 和备份 batch ID。

### 6.2 创建发布前备份

更新前执行完整备份，必须同时包含 PostgreSQL 和 MinIO：

```bash
ENV_FILE=/path/to/backup.env bash scripts/backup.sh
```

必须保存命令输出中的 `BATCH_ID`，并检查：

```bash
cat backups/<BATCH_ID>/manifest.json
cat backups/last_status.json
```

只有 PostgreSQL 成功、MinIO 失败的批次不能作为完整回滚点。Redis 默认不作为业务事实回滚源；如果 Redis 中存在不可重放队列或会话状态，必须另外导出或在发布前排空队列。

### 6.3 构建不可变产物

构建过程在临时目录完成，不能直接覆盖当前线上目录：

```bash
RELEASE_ID="$(date -u +%Y%m%dT%H%M%SZ)-<version>-<commit>"
mkdir -p "/srv/richangpim/releases/${RELEASE_ID}"
bash scripts/build_frontends.sh
```

构建结束后，将 `frontend/dist` 和 `portal/dist` 复制到发布目录，并生成 SHA-256。后端镜像必须使用不可变 tag 或 digest，不能只依赖 `latest`。

构建产物检查至少包括：

- `/`、`/admin/`、`/chat`、`/share/...` 能返回正确 HTML；
- 后台资源使用 `/admin/assets/` 前缀；
- 静态资源完整，哈希文件均可读取；
- 前端构建 ID、版本号、Git commit 与 `release.json` 一致；
- 后端 `/api/v1/health`、`/health/ready`、`/api/v1/version` 返回预期值；
- 不包含 `.env`、密钥、调试凭据或临时文件。

### 6.4 启动非活跃后端槽位

新版本先启动非活跃槽位，连接与线上相同的 PostgreSQL、MinIO、Redis，但只允许通过内部网络访问。

启动顺序：

1. 创建新容器或新服务；
2. 等待数据库、Redis、MinIO 等依赖健康；
3. 执行兼容性迁移；
4. 等待应用健康检查；
5. 执行认证、查询、上传、图片访问、AI/知识接口等关键冒烟测试；
6. 记录新槽位的版本和迁移 head。

新槽位不应直接暴露宿主机端口，避免它绕过 nginx 被用户访问。健康检查必须使用容器内部地址或专用管理网络。

### 6.5 切换流量

流量切换必须是单个配置或路由状态的原子变化：

- nginx：生成完整的新配置，执行 `nginx -t`，然后 `nginx -s reload`；
- 云端入口：切换 upstream、反向代理目标或服务发现指针；
- 公测 Node 服务：切换两个静态/代理槽位的入口，或使用稳定入口进程转发到新槽位。

切换前必须再次执行配置测试，切换后立即验证：

```bash
curl -fsS http://127.0.0.1:888/api/v1/health
curl -fsS http://127.0.0.1:888/
curl -fsS http://127.0.0.1:888/admin/
```

切换期间已建立的长连接、AI 流式响应和大文件上传需要单独处理。nginx reload 通常不会主动杀掉已有 worker，但应用槽位停止前必须等待连接排空，不能立即 `kill -9`。

### 6.6 观察期与完成发布

切换后至少观察一个发布窗口。建议默认 10 至 30 分钟，公测重大改动延长至 1 至 24 小时。

观察指标包括：

- 5xx、502、超时和连接重置；
- 登录失败率和 token 校验失败；
- 产品查询、编辑、导入和图片访问；
- MinIO 上传失败、对象数量异常；
- 数据库连接池耗尽、锁等待、慢查询；
- Redis 队列堆积和知识任务失败；
- AI 请求超时、限流和错误率；
- 磁盘、内存、CPU、容器重启次数。

观察期内保留旧后端容器、旧前端发布目录和发布前备份。观察通过后，才清理旧容器和过期产物。

## 7. 数据库迁移策略

### 7.1 必须采用 Expand/Contract

所有需要零停机的 schema 变更采用三阶段：

1. **Expand**：只新增兼容对象，例如新列、新表、新索引；旧代码仍可运行；
2. **Migrate**：应用新旧字段双写或后台批量回填，验证数据一致性；
3. **Contract**：确认所有旧版本已下线、旧字段不再被读取后，下一次发布再删除旧对象。

典型例子：字段重命名不能直接 `DROP old_name`。应先新增 `new_name`，代码双读/双写，完成回填和验证，最后在独立发布中删除 `old_name`。

### 7.2 迁移分类

| 类型 | 示例 | 是否允许热插拔 |
| --- | --- | --- |
| 兼容新增 | 新表、新 nullable 列、并发创建索引 | 允许，需验证锁和耗时 |
| 数据回填 | 新字段从旧字段计算 | 允许，必须分批、可暂停 |
| 双写切换 | 新旧结构同时写入 | 允许，需监控一致性 |
| 删除旧结构 | 删除列、表、旧枚举值 | 不与旧代码共存；需单独发布 |
| 破坏性数据变换 | 改变金额、状态、权限语义 | 默认不允许零停机，需演练和批准 |
| 大锁表操作 | 长事务、重建大表 | 默认不允许热插拔，需维护窗口 |

### 7.3 迁移失败处理

迁移失败时：

- 新槽位不得接流量；
- 旧槽位只有在 schema 仍兼容时才能继续服务；
- 记录失败 migration、数据库状态和日志；
- 不自动执行 `alembic downgrade`，除非该 downgrade 已经过真实数据演练；
- 评估是否需要使用备份恢复。

注意：Alembic 的 downgrade 不是通用回滚机制。删除列、数据覆盖、不可逆类型转换等操作即使脚本存在 downgrade，也可能无法恢复原始值。

## 8. 回滚设计

### 8.1 代码回滚

代码回滚是首选的快速回滚，目标是数十秒内完成：

1. 停止向当前新槽位发送新流量；
2. 确认旧槽位仍在观察期内且健康；
3. 将入口切回旧槽位；
4. `nginx -t` 并 reload，或切换云端服务指针；
5. 验证健康接口和关键业务；
6. 保留故障新版本，收集日志后再停止。

如果旧槽位已经停止，应使用相同镜像 digest 和旧版本发布目录重新启动，而不是依赖当前 Git 分支重新构建。

### 8.2 前端回滚

前端只要旧发布目录仍在，回滚就是原子指针切换。回滚后需要让 HTML 不缓存或刷新入口缓存，带 hash 的旧 JS/CSS 不应被删除。

不能只回滚前端而保留不兼容的后端 API；前端和后端必须按兼容矩阵成对回滚。

### 8.3 数据回滚

数据回滚是高风险操作，必须明确批准。流程：

1. 先执行一次当前状态的紧急备份，避免覆盖故障现场；
2. 停止写流量，必要时启用维护页；
3. 验证目标批次的 PostgreSQL、MinIO manifest 和 SHA-256；
4. 在隔离环境先做恢复演练；
5. 恢复 PostgreSQL 到明确目标库；
6. 恢复 MinIO 到明确目标 bucket；
7. 运行迁移 head、关键表计数、对象数量和抽样校验；
8. 启动与该数据快照兼容的应用版本；
9. 验证通过后恢复流量。

当前 `scripts/minio_restore.sh` 的接口是指定一个归档文件和明确的目标 bucket，不应把不存在的 `--batch` 参数当成现有能力。发布自动化需要先读取实际 manifest，再调用正确的恢复命令。

数据回滚通常会丢失备份时间点之后的新写入，因此必须向操作者明确显示：目标时间、备份批次、预计丢失窗口和不可逆风险。

### 8.4 回滚决策矩阵

| 故障 | 首选动作 | 是否恢复数据 |
| --- | --- | --- |
| 前端白屏、资源 404 | 回滚静态发布指针 | 否 |
| 新后端 5xx、接口异常 | 切回旧 backend 槽位 | 否 |
| 新迁移失败且 schema 未改变 | 停止新槽位，修复后重发 | 否 |
| 迁移成功但旧代码不兼容 | 先评估兼容修复；必要时数据恢复 | 视情况 |
| 误删/批量错误写入数据 | 停写并恢复目标备份 | 是 |
| MinIO 对象丢失或损坏 | 恢复 MinIO 备份 | 是 |

## 9. 本地构建版方案

本地版默认使用 Docker Compose。最终实现建议拆分为以下服务角色：

- `backend-blue` / `backend-green`：两个应用槽位；
- `nginx`：唯一对外入口，负责 upstream 切换；
- `postgres`、`minio`、`redis`：独立持久化服务，发布时不重建数据卷；
- 发布脚本：负责备份、构建、启动、健康检查、切换、观察和回滚。

本地更新禁止直接把现在的单一 `backend` 服务简单改成 `docker compose up -d backend` 后就宣称零停机。该命令会替换同一个容器，可能有连接中断，也无法在迁移失败后保留可切换的旧应用槽位。

如果主机资源不足以同时运行两个后端容器，则只能实现“数据安全的短暂停机更新”，不能实现严格零停机蓝绿更新。资源预算至少要为新旧应用同时运行预留 CPU、内存和临时磁盘。

## 10. 云端公测版方案

公测版有两个独立更新对象：

### 10.1 前端高频更新

前端和门户应使用版本目录加原子指针切换。静态资源使用内容 hash 和长期缓存，`index.html` 使用 `no-cache`，确保新壳子能找到新资源。

前端-only 发布不需要重启 backend，也不应触碰 PostgreSQL、MinIO 和 Redis。发布成功后可立即通过公开入口验证 `/`、`/admin/`、`/chat` 和 `/share/...`。

### 10.2 后端和大改动

后端使用同一套蓝绿流程。公测入口必须始终保持同源代理关系：前端、图片、文件和 `/api` 不能因切换而指向不同 origin。

公测重大改动必须先在 staging 或临时 Compose project 中完成：

1. 使用生产结构的脱敏数据库副本；
2. 使用独立 MinIO bucket；
3. 执行完整迁移和恢复演练；
4. 模拟旧版本仍在线的兼容窗口；
5. 测试回滚到旧镜像和旧前端；
6. 通过后才进入公开环境。

## 11. 发布状态机

发布脚本应持久化状态，避免脚本中断后无法判断当前流量指向：

```text
PRECHECK
  -> BACKUP_CREATED
  -> ARTIFACT_READY
  -> CANDIDATE_STARTED
  -> CANDIDATE_HEALTHY
  -> TRAFFIC_SWITCHED
  -> OBSERVING
  -> COMPLETED
```

任意阶段失败时：

- `PRECHECK`、`BACKUP_CREATED`、`ARTIFACT_READY` 失败：不改变线上服务；
- `CANDIDATE_STARTED`、`CANDIDATE_HEALTHY` 失败：停止候选槽位，不切流量；
- `TRAFFIC_SWITCHED` 后失败：按发布记录切回 previous release；
- 数据恢复过程中失败：保持停写，不能自动恢复流量，等待人工处理。

状态文件至少包含：`release_id`、`previous_release_id`、`active_slot`、`candidate_slot`、`backup_batch_id`、`migration_head`、`started_at`、`switched_at`、`status` 和错误摘要。状态文件必须原子写入。

## 12. 监控、告警与审计

每次发布必须记录：

- 操作人、开始时间、结束时间；
- 目标 Git commit、镜像 digest、前端产物摘要；
- 发布前后的版本和迁移 head；
- 备份 batch ID 和校验结果；
- 活跃槽位变化；
- 健康检查和冒烟测试结果；
- 是否发生回滚、回滚原因和最终状态。

建议告警条件：

- 新槽位健康检查连续失败；
- 切换后 5xx/502 超过基线；
- 数据库锁等待或连接池耗尽；
- MinIO 上传/读取错误上升；
- Redis 队列持续堆积；
- 备份状态不是 `ok`；
- 发布状态长时间停留在 `OBSERVING`；
- 当前 release 与记录的流量指针不一致。

## 13. 验收标准

### 13.1 正常发布

- 新旧 backend 能同时运行；
- 新版本未通过健康检查前，旧版本持续服务；
- 切流量期间无主动中断的短请求；
- 前端入口、后台入口、API、上传、图片访问均正常；
- PostgreSQL、MinIO、Redis 的 volume ID 未改变；
- 发布前备份 manifest、SHA-256 和 release.json 完整；
- 观察期结束后旧版本仍可按记录重新启动。

### 13.2 发布失败

- 候选容器失败不影响当前用户；
- 迁移失败不自动误切流量；
- 配置测试失败不 reload nginx；
- 前端构建失败不覆盖当前静态目录；
- 发布脚本中断后可从状态文件恢复判断；
- 日志中能定位失败阶段和候选版本。

### 13.3 代码回滚

- 切回旧槽位不删除数据；
- 旧前端入口能恢复；
- 回滚后健康检查、登录、查询和文件访问通过；
- 故障版本的日志和产物仍保留。

### 13.4 数据恢复

- PostgreSQL 和 MinIO 使用同一备份批次；
- SHA-256 校验失败时拒绝恢复；
- 恢复前有当前状态紧急备份；
- 恢复后表、对象、迁移 head 和关键业务抽样一致；
- 已知数据丢失窗口得到明确记录和确认。

## 14. 实施阶段

### 阶段一：先实现安全基础

- 固化 release 目录和 `release.json`；
- 增加发布状态文件；
- 将现有 backup/restore 接入发布前门禁；
- 增加候选版本健康检查和冒烟测试；
- 为每次发布保留可启动的旧镜像和前端目录。

### 阶段二：实现前端原子热切换

- 公测 Node 静态服务改为稳定入口加版本目录；
- nginx 改为版本化静态槽位或新容器切换；
- 验证 HTML、hash 资源和浏览器缓存策略；
- 支持 `frontend-only` 发布和回滚。

### 阶段三：实现后端蓝绿

- Compose 增加 blue/green 应用槽位；
- nginx upstream 支持候选槽位和原子 reload；
- 实现候选启动、健康检查、流量切换、连接排空；
- 实现观察期和代码回滚。

### 阶段四：实现迁移门禁和恢复演练

- CI 检查迁移是否符合 expand/contract；
- 建立 staging 数据恢复演练；
- 对大表、锁、回填和索引建立耗时基线；
- 每次公测重大改动必须做一次回滚演练；
- 验证 PostgreSQL 与 MinIO 联合恢复。

## 15. 关键结论

1. **前端可以做到接近真正的零停机热切换**，前提是采用版本目录和原子指针，不能逐文件覆盖在线目录。
2. **后端可以通过蓝绿部署实现无主动停机切换**，但需要两个应用槽位、入口热切换和足够资源。
3. **数据库是零停机和可回滚的核心限制**。共享数据库意味着旧、新应用必须在迁移窗口内兼容。
4. **破坏性迁移不能承诺无条件热回滚**。必须拆成 expand/contract；确实不可逆的变更需要维护窗口或接受按备份时间点恢复造成的数据丢失窗口。
5. **代码回滚和数据回滚必须分开**。绝大多数发布故障先切回代码，不要一发现错误就恢复数据库。
6. **当前命名卷设计可以保护文件和数据**，但只有在发布流程禁止 `down -v`、删除卷和覆盖在线目录的前提下才成立。
