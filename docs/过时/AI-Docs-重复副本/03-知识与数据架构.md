# 03 知识与数据架构

> 实施状态：**目标态设计，当前尚未实现。** 当前数据库只有 `product_manual`、`product_manual_chunk` 和未启用的 `product.vector`；本章新表、新流水线和混合检索必须按 `07` 分期交付。

## 1. 数据通道

### 1.1 结构化事实通道

以下字段只能由当前 PIM 业务服务读取：

- 产品编号、名称、品牌、类目、标签；
- 面价、成本价及待核价状态；
- 库存状态及其未知状态；
- 供应商；
- 产品上下架、草稿、软删除状态；
- 产品规格字段；
- 数据完整度与更新时间；
- 方案、报价、分享的当前状态。

结构化通道返回值必须附带 `observed_at` 和字段级来源。若未来接入 ERP，仍通过统一工具抽象返回，不让 Planner 直接访问外部系统。

### 1.2 非结构化证据通道

适合 RAG：

- 产品说明书、规格书、数据手册；
- 证书、安装、维护、售后资料；
- 产品长描述和培训资料；
- 经治理后纳入的 FAQ、类目和品牌知识。

动态价格、库存、成本、供应商即使出现在文档，也必须标为 `volatile_fact=true`，不进入最终事实答案。

### 1.3 模型推断通道

模型可以执行比较、归纳、语言组织和一般建议，但输出必须可区分：

- `fact`：业务工具返回；
- `evidence`：文档直接支持；
- `inference`：根据事实与证据推导；
- `general_advice`：无 PIM 专属证据的一般建议。

## 2. 目标知识模型

当前 `ProductManual` 和 `ProductManualChunk` 保留用于兼容已有说明书功能。新架构通过通用知识表承载后续来源，迁移采用双写/回填/切读，而不是直接破坏现表。

### 2.1 `knowledge_document`

| 字段 | 说明 |
| --- | --- |
| `id` | UUID |
| `source_type` | `product_manual/product/faq/category/brand/policy` |
| `source_id` | 来源对象 UUID，应用层按类型校验 |
| `product_id/category_id/brand_id` | 常用过滤维度，可空 |
| `attachment_id` | MinIO 附件，可空 |
| `title/doc_type/version/language` | 文档语义信息 |
| `content_hash` | 规范化内容哈希 |
| `parse_status/index_status` | 独立解析与索引状态 |
| `is_active` | 是否可召回 |
| `effective_at/expired_at` | 有效期 |
| `visibility` | `internal/restricted`，首期不支持 public AI |
| `required_permission` | 文档附加权限，可空 |
| `metadata` | JSONB，仅放非核心扩展元数据 |
| `parser_name/parser_version` | 可重现解析结果 |
| `last_indexed_at/create_time/update_time` | 生命周期 |

### 2.2 `knowledge_chunk`

| 字段 | 说明 |
| --- | --- |
| `id/document_id` | UUID |
| `product_id/category_id/brand_id` | 反规范化过滤字段 |
| `chunk_index` | 文档内稳定顺序 |
| `section_path` | 如“安装 > 环境要求” |
| `page_from/page_to` | 页码范围 |
| `chunk_type` | `paragraph/spec/table/warning/faq/title` |
| `chunk_text` | 原始证据文本 |
| `normalized_text` | 检索归一文本 |
| `text_search` | PostgreSQL `tsvector` 或可替换检索列 |
| `embedding` | 首期 `vector(1536)` |
| `token_count` | 实际 tokenizer 计算，不再用字符数冒充 token |
| `embedding_model/version` | 向量谱系 |
| `content_hash` | 块幂等标识 |
| `metadata` | 表格坐标、标题层级等 |

### 2.3 `knowledge_index_job`

| 字段 | 说明 |
| --- | --- |
| `id` | 任务 UUID |
| `source_type/source_id` | 索引对象 |
| `operation` | `upsert/delete/reindex` |
| `status` | `pending/dispatched/processing/succeeded/failed/dead` |
| `content_hash` | 触发时内容版本 |
| `pipeline_version` | 解析、切块和 Embedding 流水线版本 |
| `priority` | 交互上传高于批量重建 |
| `attempt_count/max_attempts` | 重试控制 |
| `next_attempt_at` | 指数退避 |
| `locked_by/locked_at/heartbeat_at` | Worker 租约 |
| `error_code/error_message` | 可运营错误，不含敏感原文 |
| `trace_id` | 端到端追踪 |
| `created_by` | 触发用户，可空 |
| 各时间字段 | created/started/completed |

幂等键：

```text
source_type + source_id + operation + content_hash + pipeline_version
```

### 2.4 会话与反馈预埋

首期不保存原始对话，但定义 `ConversationStore` 接口：

```text
create_session(metadata) -> session_id
append_turn(session_id, request_digest, response_digest, trace) -> turn_id
load_context(session_id, policy) -> messages
list_sessions(user_id, cursor) -> sessions
delete_session(user_id, session_id)
```

首期 `DigestConversationStore` 只保存摘要、哈希、来源、工具、模型和用量。未来启用 `FullConversationStore` 前必须完成保留期限、删除权、加密、访问审计和客户数据政策评审。

反馈表至少包含：`trace_id`、`turn_id`、评分、问题类型、引用是否正确、期望产品、用户备注摘要和创建人。反馈不能直接在线训练模型，只进入脱敏评测样本候选池。

## 3. 产品知识卡片

为每个产品生成稳定的检索文档：

```text
产品名称：...
产品编号：...
品牌与类目：...
材质、规格、颜色：...
标签：...
产品描述：...
适用场景：仅当 PIM 有明确字段或文档证据时写入
```

禁止写入面价、成本、库存、供应商和上下架状态。这些字段变化不触发 Embedding，只在回答时调用结构化工具。

卡片触发重建字段：名称、描述、材质、规格、颜色、标签、品牌、类目。若未来引入结构化属性体系，属性变化也触发重建。

## 4. 解析与切块

### 4.1 解析流水线

```text
附件病毒/类型检查
→ 下载至受控临时目录
→ 原生文本解析
→ 无文本时按策略 OCR
→ 标题/页码/段落/表格结构恢复
→ 文本规范化与敏感标记
→ 结构化切块
→ Embedding
→ 质量检查
→ 原子发布新索引
```

任何阶段失败均保留上一个成功索引；新索引全部成功后才切换 `active_generation`。

### 4.2 切块优先级

1. 文档标题和章节层级；
2. 段落；
3. 列表整体；
4. 参数名和值；
5. 表头加当前表格行；
6. 警告和适用条件；
7. 超出 Token 上限时再滑窗截断。

目标块大小以 300-600 tokens 为起始实验区间，重叠 40-80 tokens；最终参数由中文真实评测集决定，不写死为架构常量。

### 4.3 表格规则

- 每个表格块重复表名、表头、型号上下文；
- 不拆散“参数名-数值-单位-适用型号”；
- 合并单元格需展开为明确文本；
- 原表位置写入 metadata，来源可回到原页；
- 无法可靠解析时标记低质量，不用于高置信回答。

## 5. 混合检索

### 5.1 查询规范化

- 大小写、全半角、连字符和空白归一；
- 产品型号同时保留原值与规范值；
- 单位同义处理但不擅自换算；
- 中文同义词只来自受控业务词典；
- 提取产品编号后以 `product_id` 做硬过滤。

### 5.2 召回与融合

建议初始候选：

| 通道 | 候选数 |
| --- | --- |
| 精确产品/型号 | 最多 10 |
| 关键词/全文 | Top 30 |
| 向量 | Top 30 |
| 产品知识卡片 | Top 10 |

RRF 初始公式：

```text
score = Σ 1 / (60 + rank_channel) + exact_bonus + metadata_bonus
```

硬规则优先于分数：无权限、失效、软删除、未完成索引的内容直接排除。精确产品编号命中获得高加权，标题、规格、警告块依次加权。

### 5.3 结果多样性

- 最终上下文默认 6-10 块；
- 同一文档最多 3 块；
- 多产品比较时每个已识别产品至少 1 块，证据不存在则明确缺失；
- 相邻高度重叠块去重；
- 规格和警告优先于一般描述；
- 不让单一长文档占满上下文。

### 5.4 中文全文检索决策

首期先采用应用层分词/检索词生成配合 PostgreSQL GIN，避免生产数据库立刻引入不熟悉的扩展。用真实产品型号、行业词和中文问题评测后，再决定安装 `pg_jieba` 或 `zhparser`。扩展引入必须纳入 PG16 镜像、迁移、备份恢复和 CI 空库升级门禁。

## 6. Embedding 版本治理

记录：供应商、模型名、维度、归一方式、pipeline version 和索引时间。禁止在原列上原地改变维度。

模型切换流程：

1. 新建 embedding generation 或新列/新表；
2. 后台全量回填；
3. 离线评测；
4. 小流量影子双检索，不影响用户答案；
5. 达标后切换 active generation；
6. 保留回滚窗口；
7. 最后清理旧向量。

## 7. 索引与数据库建议

首期建议索引：

```sql
GIN (text_search)
HNSW (embedding vector_cosine_ops)
BTREE (document_id, chunk_index)
BTREE (product_id)
BTREE (category_id)
BTREE (brand_id)
BTREE (index_status, is_active)
BTREE (source_type, source_id)
```

HNSW 与业务过滤组合必须在 1 万产品、10 万块目标数据上测试召回率，不能只测试延迟。若过滤后召回不足，依次评估提高候选、iterative scan、部分索引或按高选择性维度分区。

## 8. 删除与一致性

- 产品软删除：立即在检索条件中排除，并异步删除/停用知识文档。
- 产品下架：销售推荐默认排除，内部查询可按权限显示并标注。
- 附件替换：新索引成功前旧索引继续可用；成功后原子切换。
- 附件删除：同事务写删除任务，查询层立即依据源状态排除旧块。
- 模型失败：不能把 `index_status` 标为成功。
- Worker 重复消费：依靠幂等键和 generation 避免重复块。

## 9. 数据质量门槛

知识文档进入可检索状态前必须满足：

- 来源对象仍存在且用户可访问；
- 文档类型受支持；
- 至少存在有效正文；
- 块数量、向量数量和维度一致；
- 引用定位完整；
- 无解析异常被伪装成成功；
- 内容哈希和流水线版本已记录。
