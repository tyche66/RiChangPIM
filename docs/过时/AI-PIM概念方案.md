# AI 产品信息管理平台（AI-PIM）企业级综合架构与功能需求方案

----

## 一、 项目定位与核心愿景

### 1.1 项目定位

本系统定位为**AI驱动的企业级产品信息管理平台（AI-PIM）**。它不仅仅是一个AI聊天机器人，而是以**Business API为核心**，将产品管理、供应商管理、报价管理、方案生成等传统PIM功能，与可插拔的**AI能力中心**深度融合的现代化企业基础软件。

### 1.2 核心解决痛点

* **资产沉淀**：解决产品资料、说明书散落、无序化存储及版本权限混乱问题。
* **效能流转**：降低销售新人培训成本，大幅提升产品推荐、方案整理、报价单维护与对外分享的效率。
* **数据解耦**：彻底隔离传统业务逻辑与大模型能力，确保企业核心数据的绝对真实性与AI理解能力的充分释放。

## 二、 总体架构设计（HLD）

本系统采用标准的**互联网企业级四层软件架构**，实现高内聚、低耦合。核心原则是：**业务逻辑数据库维护，AI只负责理解、生成与推荐，所有业务统一走 Business API。**

### 2.2 四层架构职责划分

| 架构分层 | 核心技术选型 | 职责说明 |
| --- | --- | --- |
| **Presentation Layer (表现层)** | Vue3, Vite, Element Plus, Pinia | 负责用户交互。区分为企业内部PC端管理后台与外部客户高内聚的分享H5页面。 |
| **Business Layer (业务层)** | FastAPI (Python) | 系统的核心枢纽（Business API）。负责处理完整的企业级业务逻辑、数据校验、权限控权，提供标准 RESTful API。 |

## 三、 AI 能力中心设计（AI Service Layer）

### 3.1 抽象设计原则

取消对单一AI平台（如 FastGPT）的强依赖，重构为**AI能力中心（AI Service Layer）**。平台仅依赖适配器层定义的统一接口，未来无论是接入开源Agent框架，还是自研RAG系统，均无需魔改业务层核心代码。

### 3.2 AI Service Adapter 接口契约定义

为合理抹平 FastGPT、Dify 和 RagFlow 在 API（如流式输出、Tool Call 格式、会话管理等）上的较大差异，我们在设计阶段锁定统一的抽象适配接口。采用 Python `abc.ABC` 或 `typing.Protocol` 形式定义接口契约如下：

```python
from abc import ABC, abstractmethod
from typing import AsyncGenerator, Dict, Any, List, Optional

class AIServiceAdapter(ABC):
    """AI 服务适配器抽象基类
    解耦业务系统与下游 AI 引擎 (FastGPT / Dify / RagFlow)，统一 API 差异
    """

    @abstractmethod
    async def chat(
        self, 
        session_id: str, 
        message: str, 
        history: List[Dict[str, str]], 
        stream: bool = False, 
        **kwargs
    ) -> Dict[str, Any]:
        """统一对话接口（非流式）
        :param session_id: 会话唯一标识，用于底层的 session 状态管理
        :param message: 当前用户输入的内容
        :param history: 历史对话上下文
        :return: 包含统一结构（answer, sources, tool_calls 等）的 Dict
        """
        pass

    @abstractmethod
    async def chat_stream(
        self, 
        session_id: str, 
        message: str, 
        history: List[Dict[str, str]], 
        **kwargs
    ) -> AsyncGenerator[Dict[str, Any], None]:
        """统一流式对话接口
        :return: 异步生成器，输出统一格式的流式数据帧 (如 SSE)
        """
        pass

    @abstractmethod
    def parse_tool_calls(self, raw_response: Dict[str, Any]) -> List[Dict[str, Any]]:
        """统一解析和转化下游平台的 Tool Call / Function Call 格式
        :return: 抹平差异后的标准化 Tool Call 列表
        """
        pass

    @abstractmethod
    async def manage_session(self, action: str, session_id: Optional[str] = None) -> Dict[str, Any]:
        """统一会话生命周期管理（创建、拉取、删除历史）"""
        pass
```

### 3.3 数据流边界：向量检索与业务数据回查

在 RAG / 智能推荐场景中，向量检索与关系型数据查询必须严格分层：

- 向量召回只负责提供“候选集”，不能直接作为最终事实数据输出。
- 对于价格、库存、供应商、客户隐私等强准确性字段，必须由 Business API 再次查询数据库并进行二次确认。
- 设计上建议将“向量召回结果 + 业务字段回查”作为一个统一执行链路，确保最终输出始终基于可信数据。 

这条边界建议在 BPM 图中显式标记为：`AI能力中心 -> Business API -> 关系型数据库` 的闭环回查路径。

### 3.4 核心应用场景与分工

AI能力中心负责提供平台所有智能能力，主要包括以下六大模块：

1. **文档知识检索（RAG）**：快速解析产品说明书、技术参数表，回答类似“该型号是否支持IP68防水？”等技术硬指标问题。
2. **产品智能推荐**：结合用户输入的标签、预算、风格、空间描述（如：预算5万、现代风、会议室），由AI理解意图后转化为标准化筛选条件调用Business API，完成精准匹配。
3. **AI方案生成与润色**：对销售勾选的产品组合进行一键式亮点提炼、行业话术修饰与推荐理由生成。
4. **AI营销文案生成**：根据产品核心参数，自动生成多渠道营销文案（小红书/朋友圈/SEO描述/短视频脚本）。
5. **AI销售与培训助手**：赋能内部员工，快速解答“XX产品与YY产品的主要核心竞争优势与区别是什么？”等话术培训。

> ⚠️ **红线原则**：AI能力中心永远**不负责**价格、库存、供应商、客户隐私等强准确性数据的维护。大模型只负责“理解与生成”，真实数据必须由 Business API 从关系型数据库中实时调取。

## 四、 核心业务流程设计（BPM）

### 4.1 产品上传与知识归档流程

```
[管理员] -> 上传产品结构化数据与附件(PDF) -> [MinerU服务] OCR自动化解析
                                                   │
[PostgreSQL] <- 写入业务数据库(结构化参数) <───────┼───────> [AI能力中心] 提取标签与向量化入库(知识库)
                                                   │
[管理员] <─ 人工最终校验与一键上架发布 <───────────┘

```

### 4.2 AI 智能产品推荐流程

```
[客户/销售] 输入模糊需求 -> [AI能力中心] 语义理解与意图拆解 -> 转换为标准结构化检索参数 (JSON)
                                                                   │
[客户/销售] <- AI组织润色话术并结构化呈现 <- [Business API] 执行多维度条件组合查询 (SQL)

```

### 4.3 销售方案生成与对外分享流程

```
[销售] 勾选产品 A, B, C -> 一键生成基础方案 -> [AI能力中心] 执行商务语境润色与推荐理由生成
                                                                   │
[客户] 手机端扫码查阅 (带权限校验) <- 生成唯一安全URL与二维码 <- [分享中心] 一键导出 PDF/生成H5

```

## 五、 系统模块与功能清单

### 5.1 用户与权限中心（RBAC）

* **多角色权限控制**：支持菜单权限、按钮权限、接口权限及**字段级权限**。
* **字段级权限实施建议**：对敏感字段（如 `cost_price`、`supplier_id`、`customer_contact` 等）需在 FastAPI 的响应序列化层做统一过滤，避免通过 ORM 查询直接泄露；同时在接口层或服务层对字段级权限进行兜底校验，形成“查询层 + 响应层”双重防线。
* **经典隔离示例**：
* **销售角色**：可查看产品参数、AI推荐、方案生成，**严禁查看成本价**。
* **采购/产品经理**：可配置产品参数、维护**成本价**与供应商链条。
* **外部客户**：无需登录，仅拥有被分享H5页面的**只读权限**。



### 5.2 产品与供应商中心

* **多维商品属性**：系统级维护产品编号、品牌、供应商、三级分类、标签、面价、成本价、材质、库存状态、多媒体文件（图片/视频/说明书PDF）。
* **高效批处理**：支持基于标准的 Excel 批量导入导出、产品一键克隆、快速上下架与归档管理。
* **供应商联动**：维护供应商基础信息、合作状态，实现一方向多（一个供应商对应多个核心产品）的供货链条追溯。

### 5.3 方案、报价与分享中心

* **一键方案生成**：勾选产品后自动拉取多媒体物料，支持AI润色，生成精美产品方案。
* **动态报价单**：支持产品数量、税率、特定折扣动态调价，一键通过 HTML 模板动态渲染并导出高保真 PDF 报价单。
* **分享安全风控**：分享链接/二维码支持配置**公开、密码保护、到期自动失效、限制访问次数**等多重安全防护。
* **分享凭证设计**：建议将分享链接的状态与访问控制统一收敛到独立的 `ShareToken` 表中，统一管理 token、密码、过期时间、访问次数上限、当前状态与审计记录，避免将这些字段散落在 `Share` 表中。

## 六、 数据库设计概要（ERD）

为支撑上述业务，系统底座预计由 **30~40 张表**构成，核心实体关系设计如下：

### 6.1 核心数据表清单

* **用户与权限**：`User`（用户表）、`Role`（角色表）、`Permission`（权限表）、`RolePermission`（角色权限关联表）。
* **产品核心域**：`Product`（产品主表）、`Category`（分类树形表）、`Tag`（标签表）、`ProductTag`（产品标签中间表）、`Brand`（品牌表）、`Supplier`（供应商表）。
* **资产与存储**：`Attachment`（文件主表）、`ProductImage`（产品图片表）、`ProductManual`（说明书及文档表）。
* **销售交易域**：`Proposal`（方案主表）、`ProposalItem`（方案明细表）、`Quotation`（报价单表）、`QuotationItem`（报价单明细表）。
* **流转与审计**：`Share`（对外分享配置表）、`ShareLog`（动态访问审计表）、`OperationLog`（系统操作日志表）、`AIConversation`（AI交互对话上下文表）。

### 6.2 关键索引与设计规约

* 所有表统一采用 `id (UUID v7)` 作为主键，必须包含 `create_time` 和 `update_time` 时间戳。
* 所有业务表统一增加 `deleted_at`（时间戳）与 `is_deleted`（布尔）字段，采用软删除规范。物理删除仅用于极端数据清理场景，默认业务层禁止直接物理删除。
* `Product` 表的 `status`（上下架）、`category_id`（分类）设立核心业务索引。
* 预留 `vector` 字段类型（利用 PostgreSQL 的 `pgvector` 插件），以便在不引入复杂向量数据库的情况下，直接在本地执行高性能的混合检索（Hybrid Search）。
* 对于多租户演进路线，建议在后续版本中在主键之外增加 `tenant_id` 作为统一分区/索引维度，当前先以单租户为主。

## 八、 系统边界与工程安全设计

### 8.1 系统边界（什么是系统不做的）

本系统**不属于** ERP、MES、CRM 或财务软件。系统通过标准 REST API 与企业现有的钉钉、企业微信、外部CRM等系统进行无缝解耦式集成，**坚决不越界处理复杂的财务对账、生产制造工序或多级客户生命周期管理**。

### 8.2 安全防护体系

* **网络与传输**：全站强制启用 HTTPS，关键敏感接口实施 Redis 令牌桶高频限流防护。
* **数据防注入**：ORM 框架层严格参数化查询，从根本上杜绝 SQL 注入与 XSS 跨站脚本攻击。
* **内容安全**：文件上传中心预留流式病毒检测与扩展名强白名单校验，防止木马文件伪装上传。

## 九、 项目实施路线图（Roadmap）与终极工程体系

### 9.0 实施补充建议（建议纳入后续文档）

为确保方案从概念设计顺滑落地，建议后续在子文档中继续补齐以下关键约束：

1. **AI Adapter 抽象接口契约**：尽早定义 `AIServiceAdapter` 的统一 Python 接口，约束 `chat / chat_stream / parse_tool_calls / manage_session` 的行为，避免后续接入 FastGPT、Dify、RagFlow 时反复改造业务层。
2. **字段级权限实现层**：对于 `cost_price`、`supplier_id` 等敏感字段，需在 FastAPI 的响应序列化层和服务/查询层做双重兜底，避免权限漏检。
3. **主键与数据治理规范**：统一采用 **UUID v7** 作为主键，所有业务表补齐 `deleted_at` 与 `is_deleted` 的软删除规范，便于后续 SaaS 化和审计追踪。
4. **分享凭证治理**：将分享链接的密码、过期时间、访问次数、状态等字段独立收敛到 `ShareToken` 表，便于权限审计与扩展。
5. **MVP 收敛**：优先打通“产品录入 → 方案生成 → H5 分享”链路，RAG 说明书问答先放到 V1，避免 MVP 范围过大影响交付质量。
6. **测试策略补档**：新增 `docs/07-测试策略.md`，覆盖接口契约测试、AI Adapter 回归测试、字段权限自动化测试等，减少人工 review 漏洞。
