# 数据卷与持久化存储

本文档是当前 `v1.9.1` 的数据持久化口径。不要把 `docs/过时/` 中的旧 Compose 示例用于恢复或部署。

## 生产卷

| 服务 | 实际 Docker volume | 容器路径 | 重要性 | 备份方式 |
| --- | --- | --- | --- | --- |
| PostgreSQL | `richangpim_go_postgres_pg16_data_20260716` | `/var/lib/postgresql/data` | 最高，业务库和向量 | `pg_dump -Fc` 为首选，卷归档仅兜底 |
| Redis | `richangpim_go_redis_data_20260716` | `/data` | 较低，可重建 | 可选卷归档 |
| MinIO | `richangpim_go_minio_data_20260716` | `/data` | 最高，图片和附件 | `mc mirror` tar 包和卷归档 |

生产 Compose 还挂载 `./backups:/data/backups:ro` 到 backend。它只是备份结果和容量状态目录，不是业务数据卷，backend 不应向其中写入备份。

## 开发挂载

`docker-compose.dev.yml` 默认使用：

- `./docker/volumes/postgres_dev` → PostgreSQL 数据目录
- `./docker/volumes/minio_dev` → MinIO 数据目录
- Redis 当前不配置持久化 bind mount

开发数据可以删除后重新初始化，但必须确认后端没有连接生产数据库。

## 备份与恢复优先级

- PostgreSQL：以 `pg_dump -Fc` 为权威备份，恢复前确认目标数据库和 migration head。
- MinIO：必须备份业务 bucket；缩略图是派生对象，可在原图存在时重建。
- Redis：缓存、限流状态和 token 黑名单可重建，不能作为业务数据的唯一来源。
- 完整备份由 `scripts/backup.sh` 使用同一 `batch_id` 生成 PostgreSQL 和 MinIO 备份，并写入 `backups/last_status.json`。
- 生产实机 PostgreSQL 没有发布 5432，备份使用 `docker exec`，详见 `README-OPS.md`。

## 卷操作安全规则

- 不使用 `docker compose down -v`，除非已明确批准删除全部生产数据。
- 不把本机原生 PostgreSQL 目录挂载给生产 Compose。
- 恢复逻辑 dump 前先停止或隔离应用写入，并确认目标库不是生产源库。
- 恢复卷归档前必须停止对应服务；卷归档是热归档时不保证事务一致性。
- 新机器上的卷名可能不同，恢复后必须用 `docker compose config` 和 `docker volume inspect` 核对实际挂载关系。
- 备份包和 `.env` 含敏感数据，只能放在受控位置并在迁移后轮换凭据。
