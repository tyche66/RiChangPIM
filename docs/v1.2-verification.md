## 2. 产品详情 500

### 2.1 真实根因

`GET /api/v1/products/{product_id}` 原先在 `_product_response()` 中先执行：

```python
ProductResponse.model_validate(product)
```

`ProductResponse.images` 使用的 `ProductImageInfo` 要求 `file_url`、`file_name` 和
`file_type`，但这些字段不在 `ProductImage` 上，而在关联的 `ProductImage.attachment`
上。产品一旦存在产品图片，Pydantic 会在 ORM 对象上读取不存在的字段并抛出
`ValidationError`，最终表现为 HTTP 500。

详情路由还曾对未明确加载的 `product.scene_images` relationship 赋值，在异步
SQLAlchemy 环境中存在触发懒加载和 `MissingGreenlet` 的风险。

### 2.2 修复方式

- 详情查询明确加载 `Product.tags`、`Product.brand`、`Product.supplier`、
  `Product.category` 和 `Product.images -> ProductImage.attachment`。
- `_product_response()` 显式展平图片附件字段，不再直接用嵌套 ORM 图片对象进行
  `ProductResponse.model_validate()`。
- 场景图继续通过关联表显式查询，过滤关联表和 `SceneImage` 的软删除状态，并加载
  `SceneImage.attachment`。
- 移除对未加载 `product.scene_images` relationship 的赋值。
- 创建和更新产品后的重新查询同时加载图片附件，避免提交后异步懒加载。
- 保持原有 `product:view` 权限、敏感字段过滤、产品软删除、图片、场景图和说明书逻辑。

### 2.3 接口语义

| 场景 | HTTP 状态 |
| --- | --- |
| 产品存在 | 200，直接返回 `ProductResponse` |
| 产品不存在或已软删除 | 404，`产品不存在` |
| 非法 UUID | 422 |
| 未登录或无权限 | 401/403 |
| 查询或序列化真实异常 | 500，不转换成 404 |

## 4. 版本接口与页面

### 4.1 后端接口

新增：

```text
GET /api/v1/version
```

- 权限：复用现有 `stats:view`，管理员按现有规则旁路权限检查。
- 只读、无业务数据库查询，不依赖产品或媒体接口。
- 不返回数据库、JWT、MinIO、AI Key 或内部地址等敏感配置。
- 缺少构建配置时返回明确开发缺省值，不返回 500。

响应示例：

```json
{
  "code": 200,
  "data": {
    "app_name": "AI-PIM",
    "backend_version": "1.2.0",
    "frontend_version": "1.2.0",
    "build_id": "1.2.0-abc1234",
    "git_commit": "abc1234",
    "build_time": "2026-07-22T12:00:00Z",
    "environment": "production",
    "api_version": "v1"
  }
}
```

### 4.2 前端页面

- 路由：`/version`
- 路由名：`Version`
- 权限：`stats:view`
- 导航位置：AI 功能栏目之后的独立菜单项，不属于产品管理子菜单。
- 页面显示前后端版本、构建 ID、Git commit、构建时间、运行环境、API 版本和最后检查时间。

## 6. 登录 500 与 Compose 凭据一致性

### 6.1 真实异常

登录接口的后端 traceback 为：

```text
asyncpg.exceptions.InvalidPasswordError:
password authentication failed for user "pim"
```

这不是管理员账号密码校验失败。开发基础设施重建 PostgreSQL 后，PostgreSQL 容器使用
`docker-compose.dev.yml` 的硬编码密码，而仍在运行的后端使用仓库根 `.env` 的另一密码，导致
后端无法连接数据库，所有需要数据库的接口均可能返回 500。

MinIO 开发服务也存在相同的硬编码凭据漂移风险。

### 6.2 修复和运维规则

- `docker-compose.dev.yml` 的 PostgreSQL 和 MinIO 改为读取与生产 Compose 一致的环境变量，
  仅在变量缺失时使用开发缺省值。
- 后端、PostgreSQL 和 MinIO 必须使用同一份受控 `.env`，不得分别维护密码。
- 修改数据库或 MinIO 凭据后，应重建所有依赖该凭据的容器，不能只重建其中一端。
- 后端启动仍按“数据库就绪 -> 迁移 -> 管理员同步 -> RBAC 种子 -> Uvicorn”执行。
- 文档和日志禁止记录实际密码；管理员密码只通过 `ADMIN_PASSWORD` 注入。

排查命令：

```bash
docker compose ps
docker compose logs --tail=200 backend
docker compose config --quiet
```

修复后通过 Nginx 实际路径验证：

```text
POST https://localhost/api/v1/auth/login -> 200
backend -> healthy
```

## 7. Alembic revision 兼容修复

已发布 revision ID `0012_product_scene_image_partial_unique` 长度超过 Alembic 默认创建的
`alembic_version.version_num VARCHAR(32)`。空库从 `0011` 升级时，Alembic 写入 `0012` 会出现：

```text
value too long for type character varying(32)
```

不能直接缩短已发布 revision ID，因为现有数据库已经记录旧 ID，直接改名会导致：

```text
Can't locate revision identified by '0012_product_scene_image_partial_unique'
```

最终处理：

- 保留原 revision ID，兼容现有部署数据库。
- 在 `0012` 的 `upgrade()` 中，在 Alembic 记录新 revision 之前，将
  `alembic_version.version_num` 扩展为 `VARCHAR(64)`。
- 继续创建 `product_scene_image` 的 active partial unique index。

涉及文件：`backend/alembic/versions/0012_product_scene_image_partial_unique.py`。
