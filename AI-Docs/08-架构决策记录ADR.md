# 08 架构决策记录 ADR

> 实施状态：本章记录已确认的目标架构决策，不代表对应代码已经交付。实际交付状态以 `01` 的事实基线和 `07` 的阶段退出记录为准。

## ADR-001：AI 是 PIM 原生查询层

- 状态：已接受
- 决策：权限、工具、索引状态和引用均由 PIM 控制，外部 AI 平台不成为第二真相源。
- 原因：动态业务字段、软删除、RBAC 和方案流程与 PIM 强耦合。
- 后果：需要自建 Knowledge Gateway；Dify/FastGPT 只能作为可选推理/工作流实验层。

## ADR-002：保持模块化单体，增加独立 Worker

- 状态：已接受
- 决策：Gateway 在 FastAPI 后端内，索引使用同代码库的独立 Worker 进程。
- 原因：目标规模只有 1 万产品/10 万块，拆微服务收益不足；索引必须与 HTTP 隔离。
- 后果：共享模型与迁移简单，但必须限制 Worker 数据库资源。

## ADR-003：PostgreSQL + pgvector 承载首期检索

- 状态：已接受
- 决策：使用 PostgreSQL 精确/全文检索和 pgvector，不引入独立向量库或 Elasticsearch。
- 原因：目标规模可控，检索需要大量业务过滤与状态一致性，现有备份运维成熟。
- 复审触发：知识块 > 300 万、核心 SLO 被持续破坏或需要独立扩缩容。

## ADR-004：正式入口统一为 Knowledge Gateway

- 状态：已接受
- 决策：Portal 不并发拼接 `/api/v1/ai/chat` 与 `/api/v1/ai/recommend`，而调用 `/api/v1/knowledge/query` 获得一致答案、产品和动作。
- 原因：并行双调用会出现理由、产品和来源不一致，无法统一审计与预算。
- 过渡：旧端点保留给现有后台，逐步标记 deprecated/internal。

## ADR-005：禁止模型生成任意 SQL

- 状态：已接受
- 决策：模型只能选择 Tool Registry 中的版本化白名单工具。
- 原因：任意 SQL 无法可靠控制权限、性能、字段泄露和写入风险。
- 后果：新增场景需要先新增领域工具，但可测试、可审计、可治理。

## ADR-006：动态事实与文档证据分离

- 状态：已接受
- 决策：价格、成本、库存、供应商、状态现场查业务服务；说明书等走 RAG。
- 原因：文档可能过期，向量检索不能保证实时与完整。
- 后果：上下文和 UI 必须显示来源类型与数据时点。

## ADR-007：采用混合检索和 RRF

- 状态：已接受
- 决策：精确、关键词和向量并行召回，使用 RRF 融合；reranker 非首期必选。
- 原因：型号、标准号和规格值不适合纯向量；RRF 简单、可解释且无需新服务。
- 后果：必须建设中文真实评测集来调参数。

## ADR-008：索引使用 PostgreSQL 任务表 + Redis Streams

- 状态：建议接受，实施前 PoC 验证
- 决策：PostgreSQL 是任务真相源，Redis Streams 提供投递和消费组；至少一次消费，业务幂等。
- 原因：已有 Redis，Streams 比 List 具备确认和 Pending 恢复能力，无需引入 RabbitMQ/Kafka。
- 后果：需要 dispatcher、consumer reclaim、dead 状态和指标。

## ADR-009：Portal 独立工程

- 状态：已接受
- 决策：新增 `portal/`，与现有管理 `frontend/` 平级，同域 Nginx 路由。
- 原因：对话式前台与 CRUD 后台在布局、包体和发布节奏上不同。
- 后果：初期会有认证/API 工具重复；稳定后抽共享包，不在 MVP 前先做大重构。

## ADR-010：全体员工可进入，能力按细粒度授权

- 状态：已接受
- 决策：新增 `ai:access/product/knowledge/quality/procurement` 等权限，底层资源权限继续生效。
- 原因：单个 `ai:use` 无法同时满足销售、采购、治理和知识场景。
- 后果：需要种子迁移、JWT 权限更新和完整角色矩阵测试。

## ADR-011：写操作采用待确认动作

- 状态：已接受
- 决策：AI 不直接改变业务状态，先生成短期 `pending_action`，用户确认后重新授权执行。
- 原因：老板已确认人审后对外，且模型输出不可直接信任。
- 后果：需要状态机、幂等、对象版本和双重审计。

## ADR-012：首期不保存原始对话但预埋 Store

- 状态：已接受
- 决策：使用 `DigestConversationStore`；定义完整会话接口但 Feature Flag 关闭。
- 原因：满足当前隐私偏好，同时避免未来重构 Gateway 和 API。
- 后果：刷新后当前会话可能丢失，首期不提供历史页。

## ADR-013：首期一个主模型，架构兼容多供应商

- 状态：已接受
- 决策：生产只配置一个主 Chat 和一个 Embedding 模型；模型切换通过评测、影子和灰度。
- 原因：减少首期复杂度和结果漂移，同时保留供应商退出能力。
- 后果：不提供终端用户模型选择器。

## ADR-014：成本与客户敏感数据默认不发外部模型

- 状态：已接受为默认安全基线
- 决策：敏感事实通过工具和确定性模板在有权限 UI 中展示，不默认进入外部生成 Prompt。
- 原因：兼容多供应商不代表已取得所有敏感数据出域许可。
- 复审触发：明确供应商合同、脱敏方案与老板书面批准。

## ADR-015：未知和缺失必须显式表达

- 状态：已接受
- 决策：待核价显示“待核价”，库存 unknown 显示“待确认”，资料缺失时拒绝推断。
- 原因：当前试点数据大量缺失，诚实表达比看似完整的答案更重要。
- 后果：推荐和采购助手的业务价值依赖持续数据治理。

## ADR-016：暂不引入通用自治 Agent

- 状态：已接受
- 决策：采用有限 Planner + 白名单工具 + 明确流程，不建设可自循环、自加工具的通用 Agent。
- 原因：业务目标明确，自治循环会放大成本、延迟和安全风险。
- 复审触发：受控流程已稳定且存在无法用固定编排解决的高价值场景。

## ADR 维护规则

- 变更已接受 ADR 必须新增“替代 ADR”，不能静默改掉历史理由；
- 每项新基础设施、数据出域或自动写动作必须先有 ADR；
- ADR 状态使用：提议、已接受、已拒绝、已替代；
- 复审必须附评测、容量、成本或安全证据，不能只基于技术偏好。
